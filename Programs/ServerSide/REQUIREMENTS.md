# サーバー要件定義

レビュー反映日: 2026-10-24。Android Web MVPではスマートフォンが録音・音声再生とユーザー操作を担当する。サーバーはSTT・LLM・TTS、会話セッションに加えて、相づちの選択・生成準備・配信判断とPi 4しっぽ制御の許可判定・MCP連携を担当する。AndroidはPi 4へ直接接続せず、Pi 4制御要求と状態表示をアプリサーバー経由で行う。Pi 4デバイスサービスはサーバーからの制限された機器指示を実行する。必要な動作と実装状況を分けて記載する。

既存のWhisper→LM Studio→Irodori-TTSパイプラインに、Android Web向けの音声アップロード、発話分割・音響特徴分析、LLMストリーム、文節TTS配信、相づち配信、停止世代のAPIコードを追加した。Web画面とAndroid WebViewも更新したが、モデル・HTTPS環境・Android実機での接続は未確認であり、MVP受け入れ完了とは扱わない。再生結果通知API・Pi 4デバイスAPIとの統合は未実装。

運用方針（ユーザー決定、2026-10-24）: GPU搭載のローカルPCでWhisper・LM Studio・Irodori-TTSを使用する。Androidは同一LocalNET内のサーバーURLへ接続し、スマートフォンで音声を録音・再生する。具体的なサーバーPC／URL、HTTPS終端、モデルの実設定と実環境接続は未確認。しっぽ制御は音声会話の初期MVP後に実施する。

## 1. 役割

```text
Android WebViewのマイク → POST音声 → Whisper(STT) → LM Studio(LLM)
Android WebViewのスピーカー ← GET音声 ← Irodori-TTS ← 返答テキスト
                                                 LLM → MCP → Pi 4デバイスAPI → サーボ
Android WebViewの設定・操作 → アプリサーバー
```

サーバーが会話セッションと設定の正本を持つ。Android WebViewがブラウザーのマイク録音・スピーカー再生を行い、サーバーはSTT・LLM・TTSを処理する。しっぽを接続する場合は、MCPが限定されたトントン要求だけを受け、GPIOやサーボ角度を直接公開しない。

## 2. セッション・停止

| ID | 必須要件 |
| --- | --- |
| SV-01 | 開始・状態取得・終了を提供し、会話履歴と処理結果をセッションごとに分離する。セッション／発話識別子と、停止前後を識別する世代または同等の仕組みを持つ |
| SV-02 | 同一セッションの発話は1往復ずつ処理する。二重送信・二重開始を検出し、過剰な要求を無制限にキューへ貯めない。並行数・待ち行列上限と過負荷応答を決める |
| SV-03 | 停止要求はSTT・LLM・TTSの完了や会話ロックを待たず受理し、音声配信・相づち予約・新しいしっぽ動作を無効化する |
| SV-04 | 停止した世代の遅着結果を配信・実行しない。外部処理を中断できない場合も、その結果は破棄する。再接続・再起動時に古い要求を再実行しない |
| SV-05 | しっぽ停止をLLMの判断から独立した制御経路で送る。要求送信、機器の受理、停止状態の確認を区別し、未確認を停止済みと返さない |
| SV-06 | 接続監視・セッション期限・動作タイムアウトを持ち、切断時は新しい動作を許可しない。復帰後は状態確認と明示的な再開が必要 |

「おやすみ」は通常の会話終了として、短い最後の返答だけを許可してから終了する。Android Web UIでの再生完了通知APIは未実装のため、現在は手動停止とターン単位の音声ストリーム再生までを実装対象とする。失敗・期限切れも扱い、終了待ちを無制限に続けない。この間の新しい相づち・しっぽ開始は抑止する。手動停止・異常停止では最後の返答も取り消す。

## 3. STT・LLM・TTS

| ID | 必須要件 |
| --- | --- |
| SV-07 | 合意した音声形式だけを受信し、長さ・容量を制限してWhisperへ渡す。スマホに任意のサーバーファイルパスを指定させない。非対応形式・破損データ・無音を明示的に扱う |
| SV-08 | 空の文字起こしではLLMやしっぽ開始へ進まない。認識に失敗した発話から動作指示を推測しない。日本語での小声の認識は実機確認する |
| SV-09 | Whisperの文字起こし全文を今回のユーザー発話（質問・依頼）としてLM Studioの `input` に明示し、過去の会話は別の文脈として渡す。質問本文をシステム指示や過去の履歴だけに置かず、空の文字起こしは送らない。処理が正常完了したターンは上限付き会話履歴へ追加する。短く自然な日本語の返答を要求し、出力上限を持つ。思考文を読み上げず、`reasoning=off` 非対応は明示的なエラーにする |
| SV-10 | 返答テキストをTTSへ渡し、Androidブラウザーが再生できる形式で配信する。設定した声を使用し、合成失敗を成功として扱わない |
| SV-11 | STT・LLM・TTS・初回音声準備・配信・全体の所要時間を区別して測定する。各段階と会話全体に期限を設け、超過時は処理状態を終了させて通知する |

Whisper・LLM・TTSのモデル、デバイス、バージョンと設定を記録する。メモ記載のモデル名は候補で、採用・性能は実機結果で確定する。初回ダウンロードやモデルロード時間は通常の会話遅延と分け、デモ前に必要ファイルを取得して準備状態を確認する。

設定画面からSilero VADの開始・終了しきい値、最小発話時間、終端の無音時間、先頭保持時間、最大発話長を検証付きで保存できるようにする。判定はサーバー側で行い、会話開始時に設定を固定する。保存により進行中の入力を中断しない。Whisper内部VADとの違いを表示する。

稼働状態APIは次の会話用設定と現在の会話で観測したモデル・デバイス・読み込み／処理／最終成功／失敗状態を区別して返す。設定されたCUDAを実際のGPU利用確認とは扱わず、外部サービスのデバイスが確認できない場合は未確認とする。状態取得はモデルロード・推論・会話の期限切れ処理・音声状態のリセットを行わない。最終成功時刻と外部接続の現在保証がないことも明示する。

### 質問・依頼本文の受渡し仕様

1. `WhisperSTT.transcribe_file()` が音声から認識した本文を `Transcription.text` に返す。
2. `VoicePipeline.process_audio_file()` は空本文なら `NoSpeechDetected` とし、LLM・TTSへ進まない。
3. 本文がある場合は `VoiceLLMClient.generate_response(transcription.text, history)` に渡す。`STTLLMTTS/llm/lm_studio.py` がLM Studioの `input` 内に「今回のユーザー発話（質問・依頼）」として本文を配置する。
4. 直近の会話履歴は同じ `input` 内で「以前の会話」として分離し、今回の発話に答えるための文脈として使う。話し方や役割の指定は `system_prompt` に置き、質問本文はそこへ入れない。
5. 生成された返答本文をTTSへ渡し、音声バイト列と形式を `VoiceTurnResult.speech` で返す。

この経路では質問本文をファイルやログへ保存しない。会話履歴は `VoicePipeline` インスタンスのメモリ内だけに保持する。

現行コードの初期設定と実装境界は次のとおり。実行時の有効値は環境設定とモデルサービス側でも確認する。

| 段階 | 現行の初期設定 | 入出力・制約 | 未確認事項 |
| --- | --- | --- | --- |
| STT | `Systran/faster-whisper-small`、日本語、CUDA / float16、モデルキャッシュ `ServerSide/whisper/` | PyAVで16kHzモノラルへ復号。0.7秒の無音で区切り、0.25〜15秒の発話区間ごとにWhisperを実行。信頼度・無音確率を算出し、基本周波数・抑揚・声量も分析する | NVIDIA GPU上のCUDA 12・cuBLAS・cuDNN 9接続、ブラウザーごとの録音形式、分割閾値、小声認識と特徴量の実音声精度 |

## 4. 相づち（MVP必須）

| ID | 必須要件 |
| --- | --- |
| SV-12 | 相づちを用意するか、いつ配信するかはサーバーが決定する。認識済み発話の返答待ちが設定時間を超える場合、サーバー側で短い相づち音声を1往復につき最大1回選択・生成準備する。事前生成・キャッシュを使う |
| SV-13 | 相づち／本返答の選択、セッション・発話・停止世代との関連付け、配信・取消をサーバーが管理する。Androidへ再生用音声と識別情報を渡し、Androidは音声出力と再生結果通知だけを行う。クライアントから相づち内容やサーバー側の再生タイミングを決めない |
| SV-14 | 最初の返答音声が相づち開始前に準備できれば相づちは省略する。相づちを配信した後に本返答が準備できた場合はAndroidの再生キューで相づちの後に再生し、音声を重ねない。停止・切断で配信と端末再生を取り消す |
| SV-15 | サーバーは相づちと本返答に同じ声を使い、同じ相づちの連続選択を避け、発話中や「おやすみ」終了処理中には追加しない。音量はAndroidの再生設定に任せ、サーバーで二重補正しない |

現行コードの相づち候補は「うん、聞いてるよ。」「そっか、話してくれてありがとう。」の2種類で、`VOICE_ACK_DELAY_SECONDS` の初期値は0.9秒。会話開始時にサーバー側で同じTTS設定の音声をバックグラウンド生成してメモリへ準備し、候補を交互に選ぶ。最初の返答音声が準備できる前にしきい値を超えた場合、NDJSONストリームへ相づちを一度だけ配信する。Android Webは受信順に相づちと返答チャンクを再生キューへ入れ、音声を重ねない。停止時はHTTPストリームと端末再生を停止し、サーバー側で世代を無効化する。再生開始・完了・失敗の個別通知APIは未実装であり、0.9秒、文言、声、Android実機での順序は未確認。

## 5. MCP・しっぽ

| ID | 必須要件 |
| --- | --- |
| SV-16 | `tap_tail`・`stop_tail`・`get_tail_status` だけを会話用に公開する。自由なサーボ角度・任意URL・任意ツール実行は受け付けない |
| SV-17 | しっぽ開始時に、現在のセッションが動作中で、設定が有効で、明確な要求があり、停止後の古い要求ではないことを制御側で確認する。プロンプトだけを許可判定にしない |
| SV-18 | LM Studio内部で遅れてMCPが実行される場合も、MCP／機器側の許可確認で停止済みセッションの開始を拒否する。外部HTTP要求の取消だけで停止を保証しない |
| SV-19 | 期間・速さ・連続動作量を制限する。短い操作の連続要求で上限を無制限に延長しない。Raspberry Pi 4側にも角度・速度・時間の制限を持たせる |
| SV-20 | HTTP成功、機器の受理、実動作／停止状態を区別する。不正JSON、未知の状態、接続失敗は機械判定可能な失敗として返し、成功を示す会話に使わない |
| SV-21 | 機器用トークン、接続先と動作許可はサーバー設定で管理する。トントン設定の無効化は処理中の動作にも適用し、停止操作は開始許可が無効でも実行可能にする |
| SV-22 | Pi 4への接続・認証・MCP呼出し・機器状態確認はサーバー側だけで行う。サーバー側の会話制御・MCP層が明確なトントン要求、設定、セッション／停止世代を検証して固定動作へ変換し、Pi 4 APIへ送る。AndroidにPi 4の接続先・機器トークン・自由な動作パラメーターを渡さない |

既存の0.5〜5秒・毎秒0.3〜1.0回というMCP引数制限はソフトウェア側の暫定上限で、しっぽの重さ・力・接触位置・騒音・発熱の確認済み範囲を示さない。Pi 4との音声・制御APIのMVP契約は [Raspberry Pi 4 API仕様](../ClientSide/Raspi4Ver/RASPBERRY_PI_API.md) に定める。デバイスサービス、アプリセッション／停止世代の連携、遅着開始の拒否と実機確認は未完了であり、有効化条件として残す。

## 6. クライアントとの契約

Android Web向けの音声API契約は [VOICE_API.md](VOICE_API.md) に記録し、開始・状態・発話アップロード・期限付き返答音声・逐次NDJSON配信・停止のコードを追加した。設定ダッシュボードAPIと同じ管理トークンを使う。相づちの判定・音声準備・配信、音響特徴の分析、Pi 4制御はサーバーが担当し、Androidは受信音声の順次再生・停止および明示的な操作要求・状態表示を担当する。Pi 4のMCP・デバイスAPIへAndroidを直接接続しない。サーバー起動、モデル接続、HTTPS、端末接続、受け入れ確認は未実施。

## 7. 設定・データ・起動

- `dashboard/web/` の設定画面で、STTモデル・言語・デバイス・計算形式・VAD、TTSモデル・声の説明、会話の話し方・返答長・質問頻度を設定できる。設定読込・保存は `GET`／`PUT /api/v1/dashboard/settings` とし、値を検証して `dashboard/data/dashboard_settings.json` に保存する。
- TTSの参照音声としてPCM WAVを `PUT /api/v1/dashboard/reference-audio` でアップロードし、`GET` で状態確認、`DELETE` で削除できる。サーバー内の固定先 `dashboard/data/reference_voice.wav` へ検証後に原子的に保存し、元のファイル名やクライアント指定パスは保存先に使わない。形式は16-bit PCM、mono/stereo、16〜48kHz、長さ1〜30秒、サイズ10MB以下に制限する。
- アップロードWAVは次に作る `IrodoriTTS` インスタンスの `ref_wav` として使う。インスタンス生成時に音声をメモリへ読み込み、保存音声の置換・削除後も進行中インスタンスは元の音声を使い続ける。音声は設定JSON・Git・ログに含めず、TTS生成時に設定されたIrodori-TTSサーバーへ送る。その他の音声形式は未対応。
- 保存したSTT・TTS設定は、新しく作る音声処理インスタンスに反映する。会話のふるまい設定は安全ルールを変えない話し方の希望としてシステムプロンプトに加える。現在進行中の会話への動的変更は行わない。
- 相づちは画面設定 `behavior.backchannel_enabled` に従う。候補の選択、音声事前生成、遅延時の配信判断はサーバー側で行い、Androidは受信順に再生する。ダッシュボードからMCP制御を有効化しない。しっぽの制御許可と停止規則はサーバー側の既存ゲートに従う。
- 現在のサーバー開発ではTLS設定を行わない。ダッシュボードサーバーは既定で `127.0.0.1` にだけbindする。同じPC上のLM Studio・Irodori-TTSはloopback HTTPで接続する。プライベートLANで画面/APIを一時的に使う場合は `NENGITSUNE_DASHBOARD_TOKEN`（32文字以上）を設定し、ファイアウォールで接続元を制限する。HTTP通信は暗号化されないため、インターネットへ公開しない。Android WebViewのマイクを使った音声往復はHTTPSが必要で、TLS終端は端末接続の受け入れ確認前に別途構成する。
- APIキーや機器トークンはサーバーの環境設定で管理し、ブラウザー、Git、ログ本文へ出さない。Android Web音声APIは管理Bearer tokenで保護し、端末接続にはHTTPSを使う。Pi 4との制御APIは別途HTTPSとデバイス認証を使う。
- 音声アップロードの一時データは必要最小限とし、成功・失敗後に削除する。返答音声はメモリ内で最大2分、停止・期限切れで削除する。履歴はセッションのメモリ内で上限を持ち、終了時に消去する。本文をログへ残す場合は明示的な設定を必要とする。
- `store=false` はLM Studioへの保存無効の要求であり、関連サービスのログ・一時データ管理も確認する。
- 起動時にモデル・実ファイルパス・LM Studio・TTS・MCP・機器の準備を確認し、利用不可の機能をスマホへ返す。再起動だけで動作を自動再開しない。
- 自作コードは `STTLLMTTS/` と `dashboard/` に分ける。設定は `dashboard/settings_store.py`、依存関係・環境設定はServerSide直下、外部ソースは `STTLLMTTS/third_party/`、Whisperモデルは `whisper/` に配置する。
- ダッシュボード設定はサーバーにのみ保存し、秘密情報、録音音声、会話本文は設定JSONへ含めない。ユーザー入力は長さ・選択肢を検証する。
- 参照音声ファイルはユーザーが明示的に登録したWAVだけを保存する。置換・削除できるようにし、保存ファイルをGitやログへ含めない。

## 9. 受け入れ条件

以下は未実施。合意済みのAPI制限と設定した段階タイムアウトを、未確認の実測段階時間・機器条件と区別し、実測結果とともに記録する。

初期音声MVPではAndroidの音声会話・相づち・停止・異常系を先に確認する。ST-03のMCP部分とST-04は、ユーザー方針により後続のしっぽ連携フェーズで確認する。

| ID | 確認内容 |
| --- | --- |
| ST-01 | Androidブラウザー録音からSTT→LLM→TTS→Android再生の1往復を完了し、各段階の時間を残す |
| ST-02 | 返答が遅い場合の相づち、返答が早い場合の省略、重複・順序逆転を確認する |
| ST-03 | STT・LLM・TTS・相づち・MCP実行待ちの各状態で停止し、遅れて音声や新しい動作が始まらない |
| ST-04 | しっぽ無効・停止済み・期限切れのセッションからのMCP開始が拒否され、停止は独立して実行される |
| ST-05 | 無音・破損／過大音声・各サービス停止・機器切断で失敗を通知し、無制限に待たず復帰できる |
| ST-06 | 二重送信・並行要求・再接続・再起動で履歴混在や古い音声／動作の再実行がない |
| ST-07 | 成功・停止・失敗で一時音声と履歴が方針どおり削除され、ログに秘密情報を残さない |
| ST-08 | ダッシュボード設定をサーバーへ保存・再読込でき、不正な値を拒否する。新しい処理インスタンスに設定が反映され、相づち必須が守られる |
| ST-09 | 有効なPCM WAVだけを制限内で保存し、破損・形式違い・長さ超過・過大ファイルを拒否する。置換・削除後も既存TTSインスタンスの参照音声が変化せず、新規インスタンスでは現在のWAVになる |
