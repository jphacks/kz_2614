# Raspberry Pi 4 デバイス API

更新日: 2026-10-24。Raspberry Pi 4が、ESP32に想定していた機能を引き継ぎ、マイク録音・スピーカー再生とMCPからのしっぽ制御を担当する。スマートフォンは操作画面、アプリサーバーはSTT・LLM・TTSとセッション管理を担当する。以下は設計契約であり、デバイスサービスや実機の動作を確認済みという意味ではない。

## 1. 接続方式

- Pi 4上にデバイスサービスを置き、アプリサーバーと `tail_mcp_server.py` から同一LAN経由で接続する。
- 音声は1発話ずつWAVデータをHTTP転送し、MVPでは連続ストリーミングやWebSocketを使わない。制御・状態はJSON REST APIとする。
- 音声を含む全APIにHTTPSを使用する。Pi 4のアドレスはDHCP予約または固定名を使い、インターネットへポート公開しない。
- すべてのAPIで `Authorization: Bearer <device token>` を検証する。トークンはアプリサーバーとPi 4のサービス設定だけに保存し、URL・スマートフォン・ログへ出さない。
- 入力音声を既定でファイル保存しない。録音・再生用データは処理後に破棄する。

## 2. 音声入出力

### `POST /api/v1/audio/capture/start`

Pi 4のマイク録音を開始する。アプリサーバーが現在のセッション・発話を指定し、Pi 4は上限時間を超えて録音しない。

```json
{
  "session_id": "UUID",
  "turn_id": "UUID",
  "stop_generation": 4,
  "max_duration_ms": 10000
}
```

受付時は `202 Accepted` と `capture_id` を返す。`POST /api/v1/audio/capture/stop` に同じ `capture_id` と停止世代を送り、録音を止めて `audio/wav` をアプリサーバーへ返す。音声をファイル保存しない。

### `POST /api/v1/audio/play`

アプリサーバーがTTS音声をPi 4へ送り、スピーカー再生を要求する。本文は `audio/wav`、要求の識別情報は `X-Session-ID`、`X-Turn-ID`、`X-Stop-Generation`、`X-Command-ID` ヘッダーで渡す。TTS側が別形式を返す場合は、アプリサーバーでWAVへ変換してから送る。

受付時は `202 Accepted` を返し、再生開始・完了・失敗は `GET /api/v1/audio/status?command_id=<UUID>` で確認する。受付成功だけで再生済みとは扱わない。

### `POST /api/v1/audio/stop`

再生中の音声と予約音声を止める。会話停止から直接呼び出し、LLMの完了を待たない。停止世代が古い再生要求はPi 4側で拒否する。

```json
{"command_id": "UUID", "session_id": "UUID", "stop_generation": 5}
```

### 音声形式の未確定値

入力・出力はWAVに統一する。入力のPCM形式、サンプルレート、チャンネル数、1発話の長さ・容量上限、Pi 4に接続するマイク・スピーカーは、使用機器を決めてから両側で合意する。これらの数値が揃うまで接続試験を完了扱いにしない。

## 3. MCPしっぽ制御

### `POST /api/v1/tail/tap`

明確なトントン要求があり、現在のセッションが許可されている場合だけ固定動作を開始する。自由なサーボ角度、GPIO、PWM値は受け付けない。

```json
{
  "command_id": "UUID",
  "session_id": "UUID",
  "stop_generation": 4,
  "duration_ms": 2000,
  "rate_hz": 0.6
}
```

- `duration_ms`: 500〜5000。
- `rate_hz`: 0.3〜1.0。
- サーボ角度、速度、加減速、GPIO制御はPi 4のデバイスサービス内で制限する。
- 同じ `command_id` の再送で二重動作させない。応答を失った場合は状態を照会し、新しいIDでタップを自動再送しない。

受付時は `202 Accepted` とし、要求受付を示すだけで物理動作の確認ではない。

### `POST /api/v1/tail/stop`

LLMの判断やトントン有効設定とは独立して、現在の動作を止める。物理停止スイッチも別に設ける。

```json
{"command_id": "UUID", "session_id": "UUID", "stop_generation": 5}
```

### `GET /api/v1/tail/status`

`idle`、`tapping`、`fault` と `active_command_id`、残り時間、手元停止状態を返す。応答はPi 4デバイスサービスの報告であり、位置センサーのない機構の物理的な停止を測定したとは限らない。

## 4. 停止・期限・エラー

- Pi 4は起動時に録音・再生・サーボ動作を自動再開しない。サーボ動作は指定時間で終了し、ネットワーク切断で動作時間を延長しない。
- 音声再生としっぽ動作はセッション・停止世代に結び付ける。停止後に遅れて届いた古い世代の要求はPi 4で拒否する。
- 手動停止・異常停止時はPi 4への停止要求を優先し、LLM完了を待たない。要求送信、Pi 4の受理、デバイス状態の確認を分ける。
- エラーはHTTPステータスと `{"ok":false,"error":{"code":"...","message":"..."}}` 形式で返し、未知の状態や不正応答を成功扱いしない。
- `tap` は冪等IDを使い、失敗時の自動再送をしない。停止は冪等とし、再試行後も状態を照会する。

## 5. 実装との境界

現在の `tail_mcp_server.py` は旧パス `/api/tail/...` を呼んでおり、上記のPi 4デバイスAPIには未対応。Pi 4側のデバイスサービス、音声入出力、セッション／停止世代、応答検証、ハードウェアの制限・手元停止は未実装・未検証である。実装と受け入れ確認が終わるまで、しっぽ制御は既定無効を維持する。
