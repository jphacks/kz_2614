## 3. 実物と通信経路

```text
ユーザーの会話
  → 会話サーバー
  → LM Studio（mcp/nen-gitsune-tail を利用）
  → stdio MCPサーバー：tail_mcp_server.py
  → HTTP / TCP 80
  → ESP32 Follower
  → GPIO18・19・21のSG90 3台
```

別のESP32 Readerは可変抵抗器を読み、従来のテレオペ指令をFollowerへ送っています。FollowerがMCPからのタップを受理すると、Readerからの指令を拒否してMCP動作を保持します。タップ終了・停止後も、自動でReaderへは戻りません。

実物は**ESP32＋SG90 3台の直列リンクでできた、キツネ型ロボットのしっぽ**です。元の資料にあるRaspberry Pi 4＋サーボ1台の構成とは変わっています。サーバーから制御する相手はFollowerです。

- 先端指令0°：丸まった側。
- 先端指令90°：ユーザーが確認した中立姿勢。
- 先端指令180°：伸びた側。
- 3台は同じPWMを受け、先端指令を各関節へ分配する。各SG90を丸ごと0°～180°回す意味ではない。
- Followerの実設定はMCP動作有効、先端指令範囲0°～180°、速度上限0.3回/秒。
- 最終実機確認時はFollowerが90°中立で保持、Readerは可変抵抗器用の通常プログラムへ復旧済み。このメモ作成時にIPや実機状態の再測定はしていない。

## 5. 接続先と有効化設定

**サーバーPCからESP32へ通信できるLANに接続してください。**こちらのPCからはESP32へ直接届かなかったため、過去の実機HTTP確認には同じWi-Fi上のReaderを一時使用しました。サーバー側PCからの到達性は別途確認が必要です。

`Programs/ServerSide/.env` に設定します。以下のIPは前回確認したFollowerの例で、DHCPで変わっていれば更新してください。

```dotenv
TAIL_DEVICE_URL=http://192.168.100.111
TAIL_CONTROL_ENABLED=true
TAIL_MCP_ENABLED=true
TAIL_MCP_PLUGIN_ID=mcp/nen-gitsune-tail
```

| 設定 | 読む側・役割 |
| --- | --- |
| `TAIL_DEVICE_URL` | MCPプロセスが読むESP32 Followerの起点URL。パスを付けない |
| `TAIL_CONTROL_ENABLED` | MCPプロセスがトントン開始を許可する。未設定の既定値はfalse |
| `TAIL_MCP_ENABLED` | 会話サーバーがLM StudioへMCP連携を渡す。未設定の既定値はfalse |
| `TAIL_MCP_PLUGIN_ID` | 会話側のプラグインID。既存の `mcp/nen-gitsune-tail` を維持 |

`TAIL_DEVICE_TOKEN`、Bearerヘッダー、APIキーの設定は不要です。旧環境にトークン変数が残っていても提案Pythonは参照しません。

コードは `load_dotenv(..., override=False)` を使います。**すでにプロセス環境にある値が.envより優先**するため、.envを直したのにfalseや古いIPのままなら起動環境も確認してください。設定変更後は、MCPプロセスと必要な会話設定を再読み込みしてください。現在進行中の音声入力・会話がある場合は、既存の運用手順に沿って反映してください。

URLは `http://<プライベートIP>` または `http://<名前>.local` の形式を使用できます。ESP32はHTTPポート80です。Python自身はHTTPサーバーを公開せず、MCPクライアントとstdioで通信します。単にターミナルからPythonを起動して待受になるのは異常ではありません。

## 6. LM StudioのMCP登録

既存のMCP登録キー `nen-gitsune-tail` を使用し、`command` をサーバーのPython実行ファイル、`args` を配置後のスクリプトの**絶対パス**に合わせます。元の例にある別ユーザーのWindowsパスをそのまま使わないでください。

Linuxの配置例（実際のパスへ変更）：

```json
{
  "mcpServers": {
    "nen-gitsune-tail": {
      "command": "/absolute/path/Programs/ServerSide/.venv/bin/python",
      "args": [
        "/absolute/path/Programs/ServerSide/STTLLMTTS/tail_mcp_server.py"
      ]
    }
  }
}
```

Windowsの場合のPythonは通常 `.venv/Scripts/python.exe` です。LM Studioを動かしているPCから読める配置を指定してください。

元の `STTLLMTTS/llm/lm_studio.py` は、すでに以下の3名称だけを許可しています。プラグインIDと名称を揃えてください。

```python
allowed_tools = ["tap_tail", "stop_tail", "get_tail_status"]
```

MCPを再読み込みし、**速度引数がない新しいツール定義**を取得してください。古い `taps_per_second` 引数の定義を使わないでください。

## 7. LLMに公開する3操作

| MCPツール | 引数 | 動作 |
| --- | --- | --- |
| `tap_tail(duration_seconds=5.0)` | 0.5～5.0秒、既定5秒 | 指定時間だけトントン。速度固定。期限で最後の指令位置を保持 |
| `stop_tail()` | なし | 直ちに停止要求を送り、その後の状態も照会。中立復帰や脱力ではない |
| `get_tail_status()` | なし | 指令状態、残り時間、モード、設定とモード上の開始可否を返す |

速度は内部で `rate_hz=0.3` を送ります。「1回」は片端への到着を指すため、先端指令0°～180°の片道は約3.3秒、指令速度は約54°/秒です。既定5秒なら大きく動きますが、2秒では両端まで届かないことがあります。

MCP結果はコンパクトなJSON文字列です。`feedback="command_only"` は**機器の指令状態であり、物理位置・接触の検出結果ではない**ことを表します。

`get_tail_status` が追加で返す主な値：

- `mode`：`teleop` / `api` / `konkon` / `neutral` / `relax`。
- `device_enabled`：ESP32側のタップ機能設定。
- `control_enabled`：MCP側の開始許可設定。
- `ready_to_tap`：モード・設定・動作範囲・速度上限から見た開始可否。中立・脱力中はfalse。
- 60秒当たりの残り時間予算は状態APIで公開していないので、`ready_to_tap=true` でも開始受付時に429となる場合がある。

「トントンして」の明示要求で開始し、「止めて」で停止してください。ツール成功時の返答は「動作指令を送りました」等、ESP32への受付が確認できた範囲にします。元の会話プロンプトにある「しっぽが動いたと伝える」表現は、物理動作を測れていない点に合わせて調整してください。

## 8. ESP32とのHTTP契約

この契約は**すでに書き込み済みのESP32 Follower向け**です。`/api/v1/tail/...` の将来案を呼ばないでください。

| メソッド・パス | 本文 | 内容 |
| --- | --- | --- |
| GET `/api/tail/status` | なし | `ok`, `state`, `enabled`, `feedback`, `angle`, `remaining_ms`, `max_rate_hz`, `start_angle`, `end_angle` 等 |
| POST `/api/tail/tap` | JSON `{"duration_ms":5000,"rate_hz":0.3}` | 受付時200、`state=tapping`。期限で停止・保持 |
| POST `/api/tail/stop` | 空でよい | 受付時200、`state=idle`。Readerの追従も停止 |
| GET `/api/status` | なし | `mode`, `pwm_enabled` 等。MCPの状態取得が追加で読む |
| POST `/api/mode` | フォーム `mode=teleop` または `mode=neutral` 等 | 操作者向けの既存モード切替。LLMのツールには公開しない |

`tap` は **JSONの2フィールドだけ**を送ります。`command_id`・`session_id`・`stop_generation` 等を追加すると現行ESP32では400になります。無期限の既存 `/api/konkon` をMCPから呼ばないでください。

ESP32は要求500～5000 ms、0.3回/秒、60秒間の受付時間合計10秒を制限します。同時に次のタップを受け付けません。期限後・停止後は最後の指令角で保持し、自動で90°へ戻したりPWMを切ったりしません。

## 9. 中立モードの解除と最初の接続確認

**前回の実機は90°中立で終了しています。IPが合っていても、中立中のtapは409になります。**提案Pythonは中立・脱力を自動解除しません。

最初にサーバーPCから状態を取得します。PowerShellでは `curl.exe`、Linuxでは `curl` を使ってください。

```sh
curl --connect-timeout 2 --max-time 4 http://192.168.100.111/api/tail/status
curl --connect-timeout 2 --max-time 4 http://192.168.100.111/api/status
```

操作者がリンクを見られる状態で、Readerのつまみを中央付近へ合わせてから、Followerのシリアルモニタ（115200 bps）で `t` を送って中立を解除します。USBがサーバーPCにない場合は手元の操作者へ依頼します。**`t` はReader追従も再開するので、つまみが0°端のままだと丸まる側へ動きます。**MCPだけの試験ならReaderを一時停止する方法もあります。

HTTPで同じ解除を行う場合も、つまみ位置と周囲を確認してから次を送ります。

```sh
curl -X POST -d "mode=teleop" http://192.168.100.111/api/mode
```

MCPの `get_tail_status()` を実行し、`ready_to_tap=true` を確認します。その後、操作者が見ている状態で `tap_tail(duration_seconds=5)` を1回実行し、期限で停止することを確認してください。

途中停止を別に試す場合は、動作中に `stop_tail()` を実行します。短時間に何度も動作要求すると60秒当たり10秒の上限に当たるため、自動再試行はしないでください。

試験後に90°中立へ戻す操作：

```sh
curl -X POST -d "mode=neutral" http://192.168.100.111/api/mode
```

`stop_tail()` と `mode=neutral` は異なる操作です。前者はその場で保持、後者は90°へ移動します。Followerを再起動すると従来の自動テレオペへ戻るため、中立状態は再起動後まで保持されません。

## 10. 会話サーバー側に残っている実装

次を現在のサーバー構成へ接続してください。

1. 新しいMCPを登録し、会話のLM Studio呼び出しで3ツールを利用できるようにする。
2. 会話の停止ボタン・セッション停止時に、LLMの返答完了を待たず、バックエンドから `POST /api/tail/stop` を送る経路を接続する。停止応答と、その後の `GET /api/tail/status` を区別して記録する。停止に開始許可フラグを要求しない。
3. 会話が停止した後は、新しい開始要求の発行を抑止する。処理中の会話・LM Studio要求の取消と停止世代の扱いを確認する。
4. ツール失敗や不明な機器応答を、会話で「動いた」「止まった」と断定しない。MCPの `isError` と `feedback` を扱う。

このPythonの停止世代は**同じMCPプロセスで、停止と重なって処理中だった開始**を検出し、停止を再送する仕組みです。停止後に、まだMCPに到着していなかった古いLLM要求を識別する情報はありません。LM Studioが自動実行するMCP呼び出しを会話側でどう中止・抑止するかは、サーバー側の接続を確認してください。

現行HTTPへ未対応の識別子を足して解決したことにしないでください。完全な世代照合には呼び出し経路・機器API双方の対応が必要です。プロトタイプの接続確認と、この未完了事項を分けて報告してください。

## 11. 検証済みの範囲と受け取り側の確認

こちらで確認済み：

- ESP32はトークンなし版へ書き込み・フラッシュ照合済み。
- 認証ヘッダーなしの実機 `GET /api/tail/status` と `POST /api/tail/stop` はHTTP 200。
- 実機の中立中の開始は409、速度0.6回/秒の開始は400。
- 以前の操作者立会い試験で、0°側から約177°までの動作、期限停止、途中停止、90°中立復帰を確認し、異音・接触等なしと報告された。これは物理角度の計測値ではない。
- 最終Pythonは22件のテストに成功。ツール定義、入力範囲、トークン不要、停止・取消・競合、通信期限、不正応答、モード・開始可否を検証。
- 実際のstdio JSON-RPCからローカルの模擬ESP32 HTTPサーバーへ3操作を通す結合テストも成功。

まだ確認していないもの：

- **この最終Pythonを、先輩の実際のLM Studioと会話サーバーへ登録した状態での動作。**
- サーバーPCから実ESP32へのネットワーク到達性。
- 先輩の会話・停止ボタンから、実機が操作・停止されること。
- 停止後の遅着要求を含む、会話全体の停止処理。

USBにはこの2ファイルだけで作業可能です。22件の検証コードはESP32側作業フォルダの `.build/test_tail_mcp_proposal.py` にあり、今回の2ファイルには含みません。受け取り側の既存テストにも、少なくとも次を追加・実行してください。

- ツール一覧が3つで、tapの引数は時間だけ。
- duration 0.5～5.0秒以外は拒否、速度は常に0.3。
- 中立・脱力時は `ready_to_tap=false`。
- HTTP失敗・不正JSON・未知状態を成功扱いしない。
- 停止は開始が無効でも送れる。
- 音声の既存経路に回帰がない。

## 12. エラーの見分け方

| 結果 | 主な確認先 |
| --- | --- |
| 接続タイムアウト | サーバーとESP32のLAN、IP変更、TCP 80、アクセスポイント |
| 400 | JSONが2フィールドか、durationの範囲、rateが0.3か |
| 401 | 古い認証ありファームウェア、または別の機器へ接続していないか |
| 403 | ESP32側のMCP機能設定 |
| 409 | 中立・脱力・別の往復動作中。まず `get_tail_status` のmodeを確認 |
| 429 | 60秒間の受付時間合計10秒に到達。自動再試行しない |
| 503 | ESP32のPWM・動作範囲の設定 |
| MCPが起動しない | commandのPython、argsの絶対パス、SDK 2系の依存 |
| IP設定を変えても変わらない | プロセス環境の値が.envより優先、再読み込み未実施 |
| `TAIL_CONTROL_DISABLED` | MCP側の `TAIL_CONTROL_ENABLED`、または機器側403を確認 |

作業完了時は、変更ファイル、実行場所、確認したHTTP/MCP結果、実物の観察結果、残る未確認事項を報告してください。USBファイルの配置だけを実機接続完了としないでください。
