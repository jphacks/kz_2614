# ESP32 2台・SG90 3台の連動制御

> 2026-10-25に `emori-ESP32` から `main` へ統合したESP32側の実装です。音声通信部品は [VoiceTCP](VoiceTCP/README.md)、引き継ぎ資料は [docs/esp32](../../../docs/esp32/README.md) に整理しました。Reader・Followerのスケッチと設定テンプレート、実機の記録、API仕様、MCP提案Python、サーバー側Codexへの引き継ぎメモをまとめています。
>
> MCP提案Pythonは `docs/esp32/history/2026-10-25_0313_tail_mcp_server.py` にあります。既存の `Programs/ServerSide/` は変更していません。引き継ぎメモは開発ブランチ `codex/raspberry-pi-implementation` の `STTLLMTTS` 配置を想定しているため、サーバーへ反映する際は対象ブランチの実際の配置を確認してください。
>
> Wi-Fiの実設定・端末ごとの `TailConfig.h`・ビルド生成物は含みません。Arduino IDEで使う際は各 `*.example.h` を対応する設定名へコピーしてください。

ESP32 を 2 台、同じ 2.4 GHz Wi-Fi に接続します。`ESP32-Reader` は可変抵抗器を読み、`ESP32-Follower` は SG90 3台へ同じ角度の指令を出します。可変抵抗器の全範囲に対して各関節の変化を約60°に抑え、同じ向きに加算される直列リンクの先端を約180°動かす設計です。**Followerは起動直後に3台を中立へ置き、Wi-Fi接続後は自動でテレオペを開始します。**一般的な ESP32 DevKitC / ESP32 Dev Module（従来の ESP32）を想定しています。ESP32-C3 などピン配置が異なる機種ではピン番号を変更してください。

## 配線

| 装置 | 部品の端子 | 接続先 |
| --- | --- | --- |
| Reader | 可変抵抗器の一端 | ESP32 の 3V3 |
| Reader | 可変抵抗器のもう一端 | ESP32 の GND |
| Reader | 可変抵抗器の中央端子 | GPIO34（ADC1） |
| Follower | SG90 1台目の橙/黄（信号） | GPIO18 |
| Follower | SG90 2台目の橙/黄（信号） | GPIO19 |
| Follower | SG90 3台目の橙/黄（信号） | GPIO21 |
| Follower | SG90 3台の赤（電源） | 共通の別電源 4.8～6 V（安定化 5 V を推奨） |
| Follower | SG90 3台の茶/黒（GND） | 別電源の GND と ESP32 の GND を共通接続 |

可変抵抗器は 10 kΩ 程度を想定します。中央端子に 5 V を印加しないでください。SG90 は ESP32 の 3V3 ピンや GPIO から給電しないでください。3台分の電流を供給できる安定化5 V別電源を用意してください。以前の4本のアルカリ乾電池で実測5.5 Vだったのは1台での確認です。3台同時の電圧・電流は未確認なので、接続後に動作中の電圧を再測定してください。サーボの軸に無理な力が掛からない状態で初回動作を確認してください。

サーボの別電源に乾電池を使う場合、単3ニッケル水素充電池4本は公称4.8 Vです。新品の単3アルカリ乾電池4本は無負荷で約6.4 Vになり得るため、電圧を測らずにSG90へ直結しないでください。前回のアルカリ乾電池4本・実測5.5 VはSG90 1台での結果です。3台を接続する場合は動作中にサーボの赤線と茶/黒線の間を測り、4.8 Vを下回る、動作が不安定になるなどの場合は十分な電流を供給できる安定化5 V電源に替えてください。電源を切り、SG90の赤線とESP32の5 V/VINをつながずに、別電源のプラスをSG90 3台の赤線へ、マイナスを3台の茶/黒線とFollowerのGNDへ接続します。ESP32をUSBで給電する場合、別電源のプラスをESP32の5 V/VINや3V3につながないでください。

GPIO34 は ADC1 なので Wi-Fi と同時に使えます。GPIO18・19・21 は各SG90のPWM信号用です。サーボの電源 GND と ESP32 の GND は必ず接続します。ESP32 の GPIO に 5 V を入力しないでください。可変抵抗器は 3V3 のまま給電します。

## 送信側・受信側の見分け方

両方のスケッチは `GPIO2` を識別用 LED 出力に使います。約 1.8 秒ごとに、**Reader（送信側）は1回**、**Follower（受信側）は2回**点滅します。COM番号は接続し直すと変わることがあり、2026-10-25の最終確認時は**ReaderがCOM12、FollowerがCOM6**でした。`millis()` を使うため、点滅のために Wi-Fi 通信やサーボ制御を待たせません。シリアルモニタ（115200 bps）にも起動時の役割を表示します。

基板に `GPIO2` 接続のユーザー LED があれば、それが点滅します。電源 LED しかない基板では、電源を切ってから **GPIO2 → 330 Ω程度の抵抗 → LEDの長い足（＋）、LEDの短い足（－）→ GND** と外付けしてください。基板上の LED が別ピンなら各スケッチの `ROLE_LED_PIN` を変更します。点灯と消灯が逆の基板では `ROLE_LED_ACTIVE_HIGH` を `false` に変更します。GPIO2 は起動時に使うピンでもあるため、外付け回路で GPIO2 を 3V3 にプルアップしないでください。

## 3台の中立位置とサーボホーンの取り付け

Followerは起動直後に**GPIO18・GPIO19・GPIO21へ50 Hz、HIGH時間1500 µs**を出します。Wi-Fi接続後、Readerからの指令で3台が可変抵抗器の位置へ動きます。Followerのシリアルモニタを115200 bpsで開き、`v` を送ると各GPIOのHIGH時間を確認できます。`n` は3台を中立位置に固定し、`d` は3台のPWMを止めて脱力モードにし、`t` は3台のテレオペを再開します。再起動でもテレオペへ戻ります。接続・再起動時はリンクの周囲を空けてください。中立・脱力モード中、Readerのテレオペと角度APIはHTTP 409で拒否されます。

3台が中立のとき最後のリンクが約90°で、3関節の回転が同じ向きに加算される配置を想定します。Readerの0°・90°・180°指令は、追加の丸まり調整が0のとき各サーボへの名目上の60°・90°・120°指令になります。今回保存した全可動範囲600～2400 µsの中央1/3を使い、3ピンへ同じ1200～1800 µsを出します。現在はユーザーの実機観察に合わせて0°側の丸まり調整を100 µs保存したため、0°指令では3ピンとも1100 µs、名目上の各関節角は約50°です。90°指令の1500 µsと180°指令の1800 µsは変わりません。`5`で0°側だけさらに丸めると下端のパルスが小さくなり、先端の実際の向きは0°の外へ出る可能性があります。先端の**目標角**と実測角度は個体差、ホーンの取り付け角、リンクの組み方によって変わります。

ホーンの位置を揃える際は、電源を切ってから3台のサーボホーンを外して配線します。電源を入れて軸が中立に落ち着いたら電源を切り、軸を回さないように希望する向きでホーンを差し込みます。歯の刻みで微妙にずれる場合は近い向きを選びます。1500 µsは**電気的な中立指令**で、各個体の機械的な正確な90°を保証する値ではありません。配線変更やホーンの付け外しは必ず電源を切って行ってください。

## 可変抵抗器の校正

Reader のシリアルモニタを **115200 bps** で開きます。Arduino IDE では送信欄に以下の **1文字だけ** を入力して送信します。改行設定はどれでも構いません。

1. `c` を送信して校正を開始する。校正中は Follower への角度送信を一時停止し、Follower は最後の指令を保持する。
2. 可変抵抗器を最小端から最大端までゆっくり回す。シリアルに `ADC raw/min/max` が表示される。
3. `s` を送信して最小値・最大値を保存する。保存後は角度送信を再開する。測定幅が 128 カウント未満なら保存せず、校正を続ける。

保存したADC範囲の最小値を **0°**、最大値を **180°** に割り当て、範囲外は端の角度に制限します。校正値はReader内の不揮発メモリに保存され、再起動後も読み込まれます。`v` は現在の生値と校正範囲を表示、`x` は校正を中止、`r` は保存値を消して `0～4095` に戻します。校正中にサーボを安全な位置へ置き、可動部に手を入れないでください。

今回の実機では可変抵抗器を両端まで動かすと **ADC生値が0～4095** に達しました。このため校正値を保存しても既定の変換範囲と同じであり、約90°のサーボ可動角が小さい原因はReaderのADC範囲ではありません。

## SG90 の可動範囲を調整する

Follower（受信側、2026-10-25の最終確認時はCOM6）のシリアルモニタを **115200 bps** で開きます。送信欄に次の **1文字だけ** を入力して送信します。改行設定はどれでも構いません。この範囲調整は**3台共通**で、実際に使うパルスは設定した全可動範囲の中央1/3です。中立モード中の1500 µsは変わりません。未校正の個体の初期値は **1000～2000 µs** です。今回のFollowerには、1台で実機確認した **600～2400 µs** を保存しています。追加の2台ではこの全範囲を個別に検証していませんが、連動時の指令は中央の1200～1800 µsだけです。

| 文字 | 動作 |
| --- | --- |
| `1` | 最小角側を50 µs広げる（下限を小さくする） |
| `2` | 最小角側を50 µs戻す |
| `3` | 最大角側を50 µs広げる（上限を大きくする） |
| `4` | 最大角側を50 µs戻す |
| `5` | 0°側を3台とも50 µs小さい角度側へ広げ、より丸くする（最大150 µs） |
| `6` | `5`の調整を50 µs戻す |
| `v` | 共通の調整値・丸まり調整量とGPIO18・19・21のHIGH時間を表示する |
| `n` | 3台を中立モードにする |
| `d` | 3台のPWMを停止して脱力モードにする（電源は入ったまま） |
| `t` | 中立モードを解除し、3台のテレオペを開始する |
| `s` | 実機で安全を確認したパルス範囲と丸まり調整量を不揮発メモリに保存する |
| `r` | 保存値を消し、初期範囲1000～2000 µs・丸まり調整0へ戻す |

可変抵抗器を0°端に置いて`5`を1回送ると、3台とも50 µsだけ小さい角度側へ広がります。丸まり具合とリンク同士の接触を見てから、必要な場合だけ次の段へ進めてください。異音・突き当たり・発熱があれば`6`で1段戻し、必要なら`n`で中立にしてください。`1`～`4`は全可動範囲の調整で、連動時の中央1/3の幅にも影響します。これらも**片端ずつ50 µs単位**で動きを見てください。外付けの部品が軸の動きを妨げない状態で試し、異常があれば電源を切ってください。ソフトウェアの調整限界500～2500 µsと丸まり調整上限150 µsは、SG90個体やリンクの安全な範囲を保証しません。実機で余裕を確認してから`s`を送ります。`GET /api/status`でも`pulse_us`と`curl_extra_us`を確認できます。

## Arduino IDE での手順

1. Arduino IDE に Espressif の `esp32` ボードパッケージを用意し、ボードを `ESP32 Dev Module` に設定します（実機の型番に合わせて変更）。追加のサーボライブラリは不要です。
2. [Reader の WiFiConfig.h](ESP32-Reader/WiFiConfig.example.h) と [Follower の WiFiConfig.h](ESP32-Follower/WiFiConfig.example.h) に、同じ Wi-Fi の `WIFI_SSID` と `WIFI_PASSWORD` を入力します。パスワードがない Wi-Fi では空文字列のままにします。これらのファイルが手元にない場合は、各フォルダの `WiFiConfig.example.h` を `WiFiConfig.h` にコピーしてください。Followerでは別途`TailConfig.example.h`を`TailConfig.h`へコピーし、動作範囲・速度上限を設定します。プロトタイプのAPIにトークン設定は不要です。Wi-Fi設定はGitへ登録しません。
3. [Follower のスケッチ](ESP32-Follower/ESP32-Follower.ino) を開き、受信側 ESP32 のポートを選択して書き込みます。シリアルモニタを **115200 bps** に設定し、表示された IP アドレスを控えます。
4. [Reader のスケッチ](ESP32-Reader/ESP32-Reader.ino) を開き、送信側 ESP32 のポートを選択して書き込みます。通常は `esp32-servo.local` を mDNS で探します。ルーターが mDNS を通さない場合は、Reader の `RECEIVER_IP` に手順 3 の IP を入れて再度書き込みます。IP が変わる環境では DHCP 予約を推奨します。
5. 起動直後は3台とも1500 µsの中立位置になり、Wi-Fi接続後は自動で可変抵抗器に追従します。Readerの指令0～180°を各サーボの名目上60～120°に分配します。動きを止めて中立に戻すときはFollowerのシリアルで`n`を送り、再開時は`t`を送ります。

Wi-Fi 情報は両方の `WiFiConfig.h` に設定済みです。これらのファイルは `.gitignore` に登録しています。接続先は ESP32 が利用できる **2.4 GHz** 帯で、SSID が周囲に発信されている必要があります。

## HTTP API

ESP32と同じWi-Fiに接続した端末から実行します。以下は今回確認した受信側IP `192.168.100.111` の例です。IPが変わった場合は読み替えてください。Windows PowerShellでは`curl.exe`を使います。

```powershell
curl.exe http://192.168.100.111/api/status
curl.exe -X POST -d "angle=90" http://192.168.100.111/api/angle
curl.exe -X POST -d "start_angle=0&end_angle=180&speed=60" http://192.168.100.111/api/konkon
curl.exe -X POST -d "angle=75" http://192.168.100.111/api/angle
curl.exe -X POST -d "mode=teleop" http://192.168.100.111/api/mode
curl.exe -X POST -d "mode=neutral" http://192.168.100.111/api/mode
curl.exe -X POST -d "mode=relax" http://192.168.100.111/api/mode
```

起動直後は3台とも1500 µsで、その後`teleop`モードでReaderの可変抵抗器に追従します。`POST /api/mode`に`mode=neutral`を送れば中立へ戻り、`mode=teleop`で再開します。`POST /api/angle`は3台共通の先端目標角`angle=0..180`を受け取り、その位置へ動かして保持します。移動速度はサーボ本体に依存します。

`mode=relax`は3台のGPIO18・19・21のPWM出力を0にして指令パルスを止めます。往復動作も中止し、脱力中の`/api/angle`・`/api/konkon`・Readerからの指令はHTTP 409で拒否します。SG90への**電源供給は続きます**。パルス停止時に保持力がどれだけ弱まるかは実機で確認してください。重力でリンクが動き得るため、支えられる状態で試してください。復帰時の`mode=neutral`は3台へ1500 µsを再出力します。`mode=teleop`で復帰する場合もまず1500 µsを出し、その後Readerのつまみ位置へ追従するため、リンクが動く可能性があります。再起動後は脱力状態を保存せず、通常どおり中立を経てテレオペへ戻ります。電源そのものを切るには別途スイッチ回路が必要です。

`POST /api/konkon`は`start_angle=0..180`、`end_angle=0..180`、`speed=1..180`を受け取ります。角度は異なる整数で指定し、`speed`の単位は先端の**指令角度の度/秒**です。現在位置から開始角度へ指定速度で移動した後、開始角度と終了角度を停止指令が来るまで往復します。20 msごとに角度指令を更新し、Wi-Fi通信を処理しながら動きます。初めて試す機体ではリンクを見ながら、狭い範囲と低速（例：`start_angle=60&end_angle=90&speed=15`）から確認してください。今回の実機では`start_angle=0&end_angle=180&speed=60`でユーザーが幅・速さとも良好、異常なしと確認しました。往復中に`POST /api/angle`を送ると往復を止めて指定角度で保持します。`mode=teleop`で可変抵抗器へ戻り、`mode=neutral`で3台を中立へ移します。シリアルの`t`/`n`でも切り替えられます。Wi-Fiが切断された場合、往復を止めて最後の角度を保持します。中立モード中の角度・往復指令、API操作中のReader指令はHTTP 409で拒否されます。

`GET /api/status`は現在のモード（`teleop`/`api`/`konkon`/`neutral`/`relax`）、先端指令角度`angle`、各サーボの名目角`joint_angle_deg`、3台共通の`pulse_us`、丸まり調整量`curl_extra_us`、GPIO番号を返します。脱力中は`pwm_enabled:false`と`pulse_us:null`・`joint_angle_deg:null`を返し、`angle`は停止前の最後の指令値を示します。往復中は`konkon_start_angle`・`konkon_end_angle`・`konkon_speed_dps`・`konkon_target`も返し、停止中は`null`です。角度は指令値であり、実測角度ではありません。再起動後はテレオペに戻ります。

POST の入力は `application/x-www-form-urlencoded` 形式です。

この API は同じ LAN 内から認証なしでアクセスできます。インターネットへ直接公開しないでください。外部から呼ぶ仕組みを追加する際は認証と HTTPS を備えた中継を設計してください。

## LLMしっぽMCPとの接続

先輩の[`tail_mcp_server.py`](https://github.com/jphacks/kz_2614/blob/main/Programs/ServerSide/STTLLMTTS/tail_mcp_server.py)が呼ぶHTTPパスに合わせ、Followerへ次の専用APIを追加しました。ユーザー指定により、プロトタイプではPython側・ESP32側ともトークン認証を削除しています。[提案Pythonファイル](../../../docs/esp32/history/2026-10-25_0313_tail_mcp_server.py)は引き継ぎ用です。現行PCのMCPとはツール契約が異なるため、丸ごと置換せず橋渡し・停止連携を実装してから使用します。

| MCPツール | FollowerのHTTP API | 内容 |
| --- | --- | --- |
| `tap_tail(duration_seconds=5.0)` | `POST /api/tail/tap` | JSON `{"duration_ms":5000,"rate_hz":0.3}`のように送る。500～5000 ms、速度は0.3回/秒に固定。3台を`TailConfig.h`の確認済み両端で動かし、期限で最後の角度を保持して停止 |
| `stop_tail()` | `POST /api/tail/stop` | 動作許可が無効でも往復を直ちに止め、最後の角度を保持。Readerのテレオペも停止する |
| `get_tail_status()` | `GET /api/tail/status`＋`GET /api/status` | 指令状態・残り時間・`mode`・設定とモード上の開始可否`ready_to_tap`を返す |

「1回のトントン」は片端への到着として扱い、要求された`rate_hz`に対し先端の指令速度を`(終了角度－開始角度)×rate_hz`度/秒にします。試験時の0°～180°・0.3回/秒では約54°/秒で、片道に約3.3秒かかります。`duration_ms=2000`では端まで届かず途中で止まる可能性があります。動きは20 ms間隔の指令値であり、実際のリンク速度や接触回数を測定していません。直近60秒に受付ける要求時間の合計は最大10秒です。連続要求中は次の開始をHTTP 409で拒否します。

`TailConfig.h`の`TAIL_MCP_API_ENABLED`は配布用の既定値では`false`です。開始・終了角度も既定は**90°・90°で、動作不可**です。接触しない両端と速度を実機で確認した後に有効化します。実機で確認済みの上限は`TAIL_TESTED_MAX_RATE_HZ=0.3`です。提案Pythonも速度を0.3回/秒に固定し、LLMに公開する引数は動作時間だけです。`stop`と`status`は開始が無効でも利用できます。`TAIL_DEVICE_TOKEN`の設定とAuthorizationヘッダーは不要です。受信側の`TailConfig.h`は`.gitignore`対象です。

専用APIの成功応答はJSONです。`state`は`idle`、`tapping`、または通常の`/api/konkon`による`moving`、`remaining_ms`はタップ中の残り時間、`feedback:"command_only"`は位置センサーによる実測ではないことを示します。機能無効は403、不正JSON・範囲外は400、実行中や中立・脱力中は409、60秒当たりの動作時間上限超過は429、PWM・未校正の動作範囲は503を返します。`/api/tail/stop`はタップ中以外にも利用でき、止めたあとReaderへ戻すときは従来の`POST /api/mode`へ`mode=teleop`を送ります。

MCPサーバー側では`TAIL_DEVICE_URL`をFollowerのIP（例`http://192.168.100.111`）に設定します。現行MCPはRaspberry Pi向けの**旧パス**を呼び、設計資料の`/api/v1/tail/...`にはまだ対応していません。この互換APIもセッションID・停止世代・要求IDを受けないため、停止後に遅れて届く古い開始要求の拒否までは保証しません。LLM側で現行セッションの許可判定と独立した停止経路を実装・確認するまで、サーバー側の`TAIL_CONTROL_ENABLED`と`TAIL_MCP_ENABLED`は無効のままにしてください。新APIの`state`と`feedback:"command_only"`はESP32が指令を受けた状態であり、物理的な尾の位置検出ではありません。既存の認証なしAPIを残しているため、ESP32は信頼できる隔離LAN内でのみ使います。

**2026-10-25の最初の5秒試験では、動作中の固定部ががたがた揺れて見えました。**PWMを止めて確認し、再試験ではユーザーが0°側から約177°までの動作と、HTTPによる途中停止・90°中立への復帰をいずれも異常なしと確認しました。その後、プロトタイプ向けにPythonとESP32のトークン認証を削除しました。現在の上限0.3回/秒を超える要求は400で拒否されます。受信側のローカル設定ではMCP専用APIが有効です。提案Pythonは3つの操作だけを公開し、先輩側では接続先URLと動作有効フラグを設定して接続します。配布用`TailConfig.example.h`は無効・未校正範囲の設定です。Followerは90°中立で保持します。**Followerを再起動すると従来どおり自動テレオペに戻り、つまみ位置へ追従します。**詳細は[統合調査メモ](../../../docs/esp32/history/2026-10-25-0222-LLMしっぽMCP統合調査.md)を参照してください。
