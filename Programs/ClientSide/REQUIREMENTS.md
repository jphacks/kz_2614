# クライアント要件定義

レビュー反映日: 2026-10-24。MVPはスマホで録音・再生する構成とする（ユーザー決定）。この文書は必要な動作を定義するもので、実装・実機確認の完了を示さない。現在、ClientSideのアプリコードは未実装。

## 1. 役割と対象

AndroidスマートフォンのWeb画面を第一対象とし、設定・開始／停止・マイク録音・音声送信・相づちと本返答の再生を担当する。STT・LLM・TTSの推論とMCPしっぽ制御はサーバー側が担当する。

```text
スマホのマイク → アプリサーバーのSTT・LLM・TTS → スマホのスピーカー
スマホの設定・操作 → アプリサーバー → MCP → ESP32 → しっぽ
```

スマホはアプリサーバーに接続する。LM Studio・TTS・ESP32の秘密情報はサーバーで保持する。ESP32側での音声入出力とスマホからのBLE直接制御は将来の構成候補とする。

## 2. MVP必須要件

| ID | 要件 | 確認する動作 |
| --- | --- | --- |
| CL-01 | 接続先と準備状態を表示する | スマホ→サーバーの接続、音声サービスの準備、しっぽの接続を区別する。APIへ接続できただけで機器も正常と表示しない |
| CL-02 | ユーザー操作で会話を開始する | マイク利用と音声再生の準備を確認し、開始の受理後に録音可能状態になる。未接続・権限拒否・二重開始を扱う |
| CL-03 | スマホで録音しサーバーへ送信する | 録音中を表示し、合意した形式・長さ・容量内の音声だけを現在のセッション／発話に関連付けて送る |
| CL-04 | 相づちと本返答をスマホで再生する | 音声の再生担当はスマホ1台とする。音声／発話／停止世代を付けて再生開始・完了・失敗・停止をサーバーへ通知する。受信完了と再生完了を区別する |
| CL-05 | 停止操作を常に使えるようにする | 録音とローカルの再生・予約を直ちに止め、LLMの回答を待たずサーバーの停止処理へ要求する |
| CL-06 | 停止後の古い結果を捨てる | 終了済みセッションや停止前の発話に対する相づち・返答が遅れて届いても再生せず、しっぽ開始を再送しない |
| CL-07 | 音量としっぽ設定を変更する | アプリの再生音量、トントンの有効／無効・速さを扱う。送信中／反映済み／失敗を分け、サーバーの確認値で反映完了とする。アプリ音量はスマホで相づち・本返答に1回だけ適用し、OSの音量設定とは区別する |
| CL-08 | 処理状態と失敗を表示する | 未接続、準備中、録音中、送信中、認識中、返答待ち、再生中、停止中、停止済み、エラーを識別できる |
| CL-09 | 切断・復帰を扱う | 切断時は新しい録音送信と再生を止める。再接続後は現在状態を取得し、ユーザー操作で再開する。古い音声・動作を自動再送しない |
| CL-10 | スマホの録音・再生権限を扱う | マイク拒否・入力デバイスなし・音声再生失敗を表示し、再操作の方法を案内する。利用可能と誤表示しない |

トントンの「有効」は動作の許可設定であり、直ちに動作を始める操作とは区別する。MVPの開始条件はユーザーの明確なトントン要求とし、会話開始だけでしっぽを動かさない。開始方法を拡張する場合はサーバー側の許可条件も同時に更新する。

## 3. 相づちと再生制御

- 相づちは必須。サーバーが現在の発話に対応する音声を用意し、スマホが一つの再生キューで本返答と調停する。
- ユーザーの発話中、録音中、本返答の再生中には相づちを再生しない。1往復につき最大1回とする。
- 本返答が先に再生可能になった場合は相づちを省略する。開始済み相づちと本返答を重ねない。
- 停止・切断・セッション終了後は、再生中・待機中の相づちと本返答を停止・破棄する。
- 相づちにも音量設定を適用し、同じ言葉の連続使用を避ける。待ち時間と候補音声は実機調整対象とする。

## 4. 手動停止と「おやすみ」

手動の停止ボタンと異常停止では、最後の返事を待たず無音にする。しっぽの停止はサーバー側へ直接要求する。機器の停止結果を確認できない場合は「停止未確認」と表示し、ボタンを押しただけで「機器停止済み」にしない。

通常の「おやすみ」は会話の終了要求として扱い、短い最後の返答を再生してから録音待ちを終了する。この間の新しい相づち・しっぽ開始は許可しない。手動停止が入れば最後の返答も取り消す。

## 5. ブラウザーと配信

スマホでマイクを使用できる安全な配信元を用意する。通常のスマホアクセスではHTTPSを使用し、マイク権限を取得する。`getUserMedia()` は安全なコンテキストと利用者の許可を要する。[ブラウザー仕様](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

録音形式はブラウザーの対応状況とサーバーの受け入れ形式の共通部分から選ぶ。`MediaRecorder.isTypeSupported()` の結果に加え、録音時の失敗も処理する。[録音形式の確認](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)

開始操作から音声再生を準備し、再生が拒否された場合は再操作を案内する。`play()` の成功確認前に再生中と表示しない。[音声再生API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)

画面ロック・バックグラウンドで継続会話する必要性と実現可否は未確定。実機確認までの暫定運用は前面表示中とし、背景移行時はローカルの録音・再生停止とセッション停止要求を行う。要求が届かない場合もサーバー／ESP32側の期限で動作が止まる必要がある。復帰時は状態確認後に手動で再開する。

## 6. サーバーとの契約

サーバー側の [外部インターフェース要件](../ServerSide/REQUIREMENTS.md#6-クライアントとの契約) に従う。開始・停止・設定反映・状態取得・音声送信・音声受信／状態通知が必要で、具体的なURL・通信方式は未確定。クライアントへサーバー上の任意ファイルパスやサービス用APIキーを渡さない。

## 7. 統合前に確定する事項

| 未決事項 | 完了条件 |
| --- | --- |
| 対象のAndroid機種・OS・ブラウザー | 録音→送信→相づち／返答再生→停止を実機で確認 |
| 画面ロック・バックグラウンド | 継続会話の要否を決め、必要なら実機で継続・停止・復帰を確認。未確認の間は前面表示でデモする |
| 録音の開始／終了操作 | 手動録音または発話区切りを決定。MVPは1往復ずつ処理する。録音中の再生による回り込み対策も確認 |
| 音声形式、長さ・容量上限 | 録音形式とサーバーデコード、TTS再生形式の共通仕様を記録 |
| 配信URL・接続方式・認証 | HTTPSを含むスマホ実機接続を確認し、開始・停止・設定の契約を記録 |
| 応答・停止・接続監視の期限 | 数値をサーバー・機器側と共通化し、期限超過時の表示と停止を確認 |
| 相づちの待ち時間と切替 | 本返答の到着順にかかわらず重複しないことを確認 |

## 8. 受け入れ条件

以下は未実施。機能一覧や画面表示だけで合格にせず、対応するサーバー／実機結果を記録する。

| ID | 確認内容 |
| --- | --- |
| CT-01 | マイク許可と拒否の双方を扱い、録音中表示が実際の状態に一致する |
| CT-02 | 音声1往復と相づちをスマホで再生でき、相づち・発話・本返答が重ならない |
| CT-03 | 認識中・LLM処理中・相づち中・本返答中に停止し、遅着音声を再生しない |
| CT-04 | しっぽの無効化と設定の反映確認が一致し、停止未確認を停止済みと表示しない |
| CT-05 | 切断・再接続・画面復帰後に古い音声や動作を再開しない |
| CT-06 | 「おやすみ」の最後の返事と、手動停止による即時無音を区別できる |

声・キャラクター・自発的に話す頻度の詳細設定、睡眠時間表示、通知、2台連携は拡張対象とする。
