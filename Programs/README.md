# 添い寝ロボット「ねんぎつね」（仮）— Programs

寝る前の寂しさに寄り添う、きつね型の添い寝クッションを動かすソフトウェアの概要と実装方針です。名前・構成・モデルは検討中の案を含み、確定していない項目はその旨を記載しています。

MVPの音声入力・再生はスマホが担当する方針に2026-10-24に確定しました。クライアントの必須動作は [ClientSide/REQUIREMENTS.md](ClientSide/REQUIREMENTS.md)、サーバーの必須動作と現行コードとの差分は [ServerSide/REQUIREMENTS.md](ServerSide/REQUIREMENTS.md) にまとめています。要件の記載と実装・受け入れ完了は区別します。

> `emori-ESP32` ブランチの追加実装：ESP32 2台とSG90 3台によるしっぽ制御を [ClientSide/ESP32](ClientSide/ESP32/README.md) に収録しました。配線・Arduino IDEでの設定・実機記録・HTTP API・MCP提案は同フォルダを参照してください。以下に残るESP32未実装・構成未定の記述は当初の設計段階の内容です。既存のServerSideコードは今回変更していません。

## 目指す体験

ユーザーがきつね型の枕に頬を乗せて近くのスマホへ話しかけると、スマホから相づち・返事があり、明確にトントンを求めると柔らかいしっぽが肩や上腕の近くで優しく動きます。会話のあと「おやすみ」を伝え、短い最後の返事で終了します。停止ボタンは最後の返事を待たず停止します。

電子機能が使えないときも、枕として使えることを基本にします。まず1台で会話・トントン・停止までを通し、2台連携はその後に検討します。

## 最小構成（MVP）

- 枕として使える本体と、柔らかいしっぽ
- 短い音声会話を1往復できること
- 返答待ちに、発話を遮らない短い音声の相づちを返せること
- 会話に合わせてしっぽを小さくトントンさせられること
- ユーザーが手元で停止できること
- 通信切断やタイムアウト時に、しっぽを停止できること
- 電子機能を停止しても枕として使えること

睡眠時間の記録、眠気の推定、夕方の通知、長期記憶、細かな人格設定、2台連携はMVPの後に検討します。

## プログラムの構成案

このリポジトリの `ClientSide` と `ServerSide` を、次の役割に分ける想定です。LLMとしっぽ制御のMCP境界は追加しました。ESP32とのHTTP APIは実装に向けた暫定契約で、ファームウェアと通信確認が残っています。

### ClientSide（スマホの録音・再生と設定Web画面）

- 接続先と接続状態の表示
- マイク権限、録音中の表示、音声の録音・サーバー送信
- 相づち・本返答の再生と、重複・遅着音声の破棄
- 会話・トントンの開始／停止
- 音量、トントンの有効／無効と速さの設定
- 設定の適用確認と、停止未確認・切断・再生失敗の表示
- 声、キャラクター、話す頻度の設定（MVPでは後回しでもよい）
- Androidスマートフォンを優先して動作確認

MVPはスマホが録音・再生を担当します。Android実機、ブラウザー、HTTPS配信、録音／再生形式とAPIは統合前に確定・確認します。画面ロック中の継続会話は要否・実現可否とも未確定で、暫定運用は前面表示とします。

### ServerSide（会話処理・連携の案）

- 音声認識（STT）→返答生成（LLM）→音声合成（TTS）の一連の処理
- 相づち・本返答音声のスマホへの配信
- 会話セッションの開始・終了管理
- LLMからMCP経由でしっぽの開始・停止・状態確認を呼び出す
- MCPサーバーからESP32への動作指示（暫定HTTP API）
- 失敗・切断・タイムアウト時の停止処理

自作コードは `ServerSide/app/` にまとめました。`voice_stt.py` と `voice_pipeline.py` がWhisper文字起こしをLM Studioへ渡し、モデルは `ServerSide/models/whisper/` に保存します。外部プログラムは `ServerSide/third_party/` に分けています。`tail_mcp_server.py` は `tap_tail`、`stop_tail`、`get_tail_status` の3つだけを公開し、自由なサーボ角度指定は受け付けません。しっぽ操作はユーザーが明確に希望した場合に限るプロンプトとし、MCP有効化は既定でオフです。詳細は [ServerSideの構成](ServerSide/README.md) と [自作ServerSideアプリの説明](ServerSide/app/README.md) を参照してください。

モデル候補としてメモに `faster-whisper-small`（STT）、`Gemma 4 26B-A4B（Q4_K_M）`（LLM）、`Irodori-TTS 600M v3 VoiceDesign`（TTS）が挙がっています。採用、動作環境、応答速度はいずれも未確認です。

### ESP32・しっぽ機構（ファームウェアの配置先は未定）

- SG90サーボで、軽い布・スポンジ製のしっぽを小さく上下させる案
- サーボの電源は試作時に外部5V有線給電とし、制御基板との給電経路を確認する
- サーボ信号とESP32のGNDを共通化する
- 手元で停止できる操作と、動作タイムアウトを設ける
- 0〜12°はCAD上の表示例であり、実機の角度・押す強さ・騒音・発熱は実物で調整する

ESP32の型番、サーボ電源の適合、ファームウェアのリポジトリ上の配置先は未確定です。MVPのマイクとスピーカーはスマホを使用します。

## データの流れ（概念）

```text
スマホ録音 → サーバー(STT → LLM → TTS) → スマホ再生
                              │
                              └─ MCP → tail_mcp_server → HTTP → ESP32 → SG90
スマホ設定・開始／停止 → アプリサーバー（APIは未実装）
```

MVPはスマホとアプリサーバー間で音声・設定・状態を送受信します。HTTP／WebSocketの使い分けと音声形式は未確定です。しっぽはMCPサーバーからESP32へHTTPで送る暫定契約で、ESP32側は未実装です。BLE直接制御とESP32側の音声入出力は将来の構成候補です。

## 動作の流れ

1. ユーザーがスマホ画面で開始し、マイクと再生の準備を確認する。
2. スマホの録音をサーバーへ送り、STT・LLM・TTSで短い返答を作る。
3. 返答の生成に時間がかかる場合は、相づちを短く一度だけ再生する。
4. 返答を再生し、必要に応じてしっぽを優しくトントンさせる。
5. 「おやすみ」は最後の短い返事で終了する。停止ボタンは即時に録音・再生を止め、LLMの完了を待たずしっぽ停止を要求する。
6. 通信断、異常、またはタイムアウト時は、しっぽを停止できる状態にする。

音声の開始条件、返答中のトントン動作、タイムアウト時間などの細部は実機統合時に決定します。

## 相づち（MVP必須要件）

返答を待つユーザーに、聞いていることを伝える短い音声の相づちを提供します。相づち機能自体は必須とし、再生タイミングや使用する言葉は実機で調整します。

- ユーザーの発話中には再生せず、発話が終わってから返答を待つ間に使う。
- LLMの返答を待たせる場合に、短い相づちを1回だけ再生する。返答音声と重ねない。
- 「うん」「そっか、聞いてるよ」など安心感のある短い候補を用意し、同じ言葉を連続で繰り返さない。
- 夜間に大きな音で驚かせないよう、相づちも設定音量に従う。停止・おやすみ操作後は再生しない。
- AI_Secretaryにある相づち音声の事前生成・キャッシュと、最初のLLM文節が届くまでの待ち時間を埋める処理を再利用候補とする。

相づちの種類、再生までの待ち時間（参考実装では約0.9秒）、音量、候補の切替方法は未確定です。TTS・再生・相づち制御は未実装です。

受け入れ条件は、返答待ちが設定時間を超えた際に1往復につき最大1回だけ再生すること、ユーザーの発話や本返答に重ならないこと、停止操作で再生中・待機中の相づちを停止できることです。本返答が先に準備できた場合は相づちを省略します。

## 実装・確認の順序

1. ESP32からサーボを小さい動作範囲で動かし、停止できることを確認する。
2. STT → LLM → TTSで短い音声の一往復を確認し、返答時間を測る。
3. ESP32に暫定HTTP APIを実装し、MCP Inspectorからタップ・停止・状態取得を確認する。
4. LM StudioへMCPサーバーを登録し、明示的な「トントンして」でだけツールを呼ぶことを確認する。
5. 設定画面と音声経路を接続し、1台で「開始 → 会話 → トントン → 終了」を統合する。
6. 実機で停止・再起動・通信切断からの復帰を確認してから、2台連携を試す。

## 仕様を確定する項目

- スマホ録音・再生の音声形式、最大長・容量、HTTPS配信先とAPI
- スマホとサーバー間のHTTP／WebSocketの用途、通知・再接続方法
- セッションと停止世代の識別、遅着結果とMCP動作を拒否する方法
- ESP32に実装するHTTP APIと認証方法（MCPサーバー側の契約案あり）
- ESP32側の角度制限、ウォッチドッグ、停止手段をどう検証するか
- ESP32の型番、電源容量と配線
- サーボの実機動作範囲、しっぽの接触位置、停止時間
- STT／LLM／TTSの採用モデル、サーバー・GPU環境、応答速度
- 設定項目、通信メッセージ、音声形式、切断時の再接続方法
- 2台連携をデモの必須要件とするか
- ロボットの正式名称、キャラクターの口調

## デモの基本シナリオ

「今日はちょっと寂しい」→枕に頬を乗せスマホへ話す→相づち・短い返事→「トントンして」→しっぽがトントンする→「おやすみ」→短い返事のあと静かに停止する。

入眠する場面はデモ上の演出です。会話と動作が使えない場合でも、枕として使える状態を保ちます。
