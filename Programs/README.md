# 添い寝ロボット「ねんぎつね」（仮）— Programs

寝る前の寂しさに寄り添う、きつね型の添い寝クッションを動かすソフトウェアの概要と実装方針です。名前・構成・モデルは検討中の案を含み、確定していない項目はその旨を記載しています。

更新後のMVPではRaspberry Pi 4が音声入出力とMCPしっぽ制御を担当し、Androidスマートフォンは操作画面、アプリサーバーはSTT・LLM・TTSを担当します。Web設定ダッシュボードは `ServerSide/web/` に配置し、サーバーから配信します。必須動作と現行コードとの差分は各要件書にまとめ、実装・受け入れ確認と区別します。

## 目指す体験

ユーザーがスマートフォン画面から会話を始め、枕のPi 4に接続したマイクへ話しかけます。Pi 4のスピーカーから相づち・返事があり、明確にトントンを求めると柔らかいしっぽが動きます。停止ボタンは最後の返事を待たず音声としっぽを停止します。

電子機能が使えないときも、枕として使えることを基本にします。まず1台で会話・トントン・停止までを通し、2台連携はその後に検討します。

## 最小構成（MVP）

- 枕として使える本体と、柔らかいしっぽ
- 短い音声会話を1往復できること
- 返答待ちに、発話を遮らない短い音声の相づちを返せること
- 会話に合わせてしっぽを小さくトントンさせられること
- ユーザーが手元で停止できること
- 通信切断やタイムアウト時に、しっぽを停止できること
- 電子機能を停止しても枕として使えること

睡眠時間の記録、眠気の推定、夕方の通知、長期記憶、細かな人格設定、2台連携はMVPの後に検討します。

## プログラムの構成案

このリポジトリの `ClientSide` と `ServerSide` を、次の役割に分ける想定です。LLMとしっぽ制御のMCP境界を追加し、Pi 4向けの音声・サーボAPI案を [Raspberry Pi 4 API仕様](ServerSide/RASPBERRY_PI_API.md) にまとめました。デバイスサービスと実機確認は未完了です。

### ClientSide（Androidブラウザーを基本とするスマホ画面）

- 接続先と接続状態の表示
- 会話開始／停止、Pi 4の音声入出力・しっぽ状態の表示
- 相づち・本返答の再生結果と、重複・遅着音声の確認
- 会話・トントンの開始／停止
- 音量、トントンの有効／無効と速さの設定
- 設定の適用確認と、停止未確認・切断・再生失敗の表示
- 声、キャラクター、話す頻度の設定（MVPでは後回しでもよい）
- Androidスマートフォンを優先して動作確認

設定ダッシュボードは `ServerSide/web/` に作成し、STT・TTS・会話のふるまいを保存できます。Irodori-TTS用の参照WAVもアップロード・保存・削除でき、サーバーが形式・長さ・容量を検証します。Pi 4の録音・再生・MCP制御をつなぐデバイスサービス、HTTPS配信、音声形式は未完成です。Android実機での確認と、画面ロック中の継続会話の要否も残っています。

### ServerSide（会話処理・連携の案）

- `web/` の設定ダッシュボードと、サーバー側の設定保存API

- 音声認識（STT）→返答生成（LLM）→音声合成（TTS）の一連の処理
- Pi 4で録音した音声の受信と、相づち・本返答音声のPi 4への配信
- 会話セッションの開始・終了管理
- LLMからMCP経由でしっぽの開始・停止・状態確認を呼び出す
- MCPサーバーからRaspberry Pi 4への固定動作指示（HTTPS/JSON API）
- 失敗・切断・タイムアウト時の停止処理

自作コードは `ServerSide/app/` にまとめました。`voice_pipeline.py` が音声ファイルから文字起こし・返答生成・音声合成を行います。Pi 4の音声デバイス連携と配信は未実装です。詳細は [ServerSideの構成](ServerSide/README.md) と [自作ServerSideアプリの説明](ServerSide/app/README.md) を参照してください。

モデル候補として `faster-whisper-small`（STT）、`Gemma 4 26B-A4B（Q4_K_M）`（LLM）、`Irodori-TTS 600M v3 VoiceDesign`（TTS）をコードの初期設定にしています。接続先・デバイス設定とパイプラインは実装しましたが、モデルの準備、動作環境、応答速度は未確認です。

### Raspberry Pi 4・音声入出力としっぽ機構

- マイク録音とスピーカー再生をPi 4で行い、音声データをアプリサーバーと送受信する
- SG90サーボで軽い布・スポンジ製のしっぽを小さく上下させる
- サーボは外部5V有線給電とし、Pi 4のGNDと共通化する。GPIOからサーボ電源を取らない
- 電源を切れる手元停止と、Pi 4側の動作タイムアウトを設ける
- 0〜12°はCAD上の表示例であり、実機の角度・押す強さ・騒音・発熱は実物で調整する

Pi 4に接続するマイク・スピーカー、音声入力形式、サーボ信号回路、デバイスサービスの配置先は未確定です。使用機器を決めてから録音・再生と安全性を実測します。

## データの流れ（概念）

```text
Pi 4マイク → サーバー(STT → LLM → TTS) → Pi 4スピーカー
                                  │
                                  └─ MCP → tail_mcp_server → HTTPS → Pi 4 GPIO → SG90
スマホ操作画面 → アプリサーバー → Pi 4デバイスサービス
```

音声はPi 4とアプリサーバー間で1発話ずつWAV転送する案です。制御・音声にセッションと停止世代を付け、停止後に遅れて届く要求を破棄します。音声形式の詳細、デバイスサービス、実機確認は未完了です。

## 動作の流れ

1. ユーザーがスマホ画面で開始し、Pi 4のマイク・スピーカーの準備を確認する。
2. Pi 4の録音をサーバーへ送り、STT・LLM・TTSで短い返答を作る。
3. 返答の生成に時間がかかる場合は、相づちを短く一度だけ再生する。
4. Pi 4のスピーカーで返答を再生し、必要に応じてしっぽを優しくトントンさせる。
5. 「おやすみ」は最後の短い返事で終了する。停止ボタンは即時に録音・再生を止め、LLMの完了を待たずしっぽ停止を要求する。
6. 通信断、異常、またはタイムアウト時は、しっぽを停止できる状態にする。

音声の開始条件、返答中のトントン動作、タイムアウト時間などの細部は実機統合時に決定します。

## 相づち（MVP必須要件）

返答を待つユーザーに、聞いていることを伝える短い音声の相づちを提供します。相づち機能自体は必須とし、再生タイミングや使用する言葉は実機で調整します。

- ユーザーの発話中には再生せず、発話が終わってから返答を待つ間に使う。
- LLMの返答を待たせる場合に、短い相づちを1回だけ再生する。返答音声と重ねない。
- 「うん」「そっか、聞いてるよ」など安心感のある短い候補を用意し、同じ言葉を連続で繰り返さない。
- 夜間に大きな音で驚かせないよう、相づちも設定音量に従う。停止・おやすみ操作後は再生しない。
- AI_Secretaryにある相づち音声の事前生成・キャッシュと、最初のLLM文節が届くまでの待ち時間を埋める処理を再利用候補とする。

相づちの候補音声を事前生成する処理と、LLM待ちが設定時間を超えた場合の再生コールバックは実装済みです。待ち時間の実機調整、Pi 4への配信・再生完了連携、停止時の破棄は未実装です。

受け入れ条件は、返答待ちが設定時間を超えた際に1往復につき最大1回だけ再生すること、ユーザーの発話や本返答に重ならないこと、停止操作で再生中・待機中の相づちを停止できることです。本返答が先に準備できた場合は相づちを省略します。

## 実装・確認の順序

1. Pi 4からサーボを小さい動作範囲で動かし、停止できることを確認する。
2. STT → LLM → TTSで短い音声の一往復を確認し、返答時間を測る。
3. Pi 4デバイスサービスにAPIを実装し、MCP Inspectorからタップ・停止・状態取得を確認する。
4. LM StudioへMCPサーバーを登録し、明示的な「トントンして」でだけツールを呼ぶことを確認する。
5. 設定画面と音声経路を接続し、1台で「開始 → 会話 → トントン → 終了」を統合する。
6. 実機で停止・再起動・通信切断からの復帰を確認してから、2台連携を試す。

## 仕様を確定する項目

- Pi 4の録音・再生の音声形式、最大長・容量、HTTPS配信先とAPI
- スマホとサーバー間のHTTP／WebSocketの用途、通知・再接続方法
- セッションと停止世代の識別、遅着結果とMCP動作を拒否する方法
- MCPとPi 4でセッション許可・停止世代を連携し、遅れて届く開始要求を拒否する方法
- Raspberry Pi 4側の角度制限、ウォッチドッグ、電源遮断式の停止手段をどう実装・検証するか
- Pi 4の電源容量、GPIO信号回路と配線
- サーボの実機動作範囲、しっぽの接触位置、停止時間
- STT／LLM／TTSの採用モデル、サーバー・GPU環境、応答速度
- 設定項目、通信メッセージ、音声形式、切断時の再接続方法
- 2台連携をデモの必須要件とするか
- ロボットの正式名称、キャラクターの口調

## デモの基本シナリオ

「今日はちょっと寂しい」→枕に頬を乗せPi 4のマイクへ話す→相づち・短い返事→「トントンして」→しっぽがトントンする→「おやすみ」→短い返事のあと静かに停止する。

入眠する場面はデモ上の演出です。会話と動作が使えない場合でも、枕として使える状態を保ちます。
