# 添い寝ロボット「ねんぎつね」（仮）— Programs

寝る前の寂しさに寄り添う、きつね型の添い寝クッションを動かすソフトウェアの概要と実装方針です。名前・構成・モデルは検討中の案を含み、確定していない項目はその旨を記載しています。

更新後のAndroid Web MVPではスマートフォンが音声入出力と操作画面、アプリサーバーがSTT・LLM・TTSと会話セッション管理を担当します。Raspberry Pi 4はMCP経由のしっぽ制御先として扱います。設定ダッシュボードと音声会話画面は `ServerSide/web/` に置き、サーバーから配信します。必須動作と現行コードとの差分は各要件書にまとめ、実装・受け入れ確認と区別します。

## 目指す体験

ユーザーがAndroid画面から会話を始め、スマートフォンのマイクに話しかけます。返答音声はスマートフォンで再生し、明確にトントンを求めるとPi 4につないだ柔らかいしっぽが動きます。停止ボタンは最後の返事を待たず端末の音声処理と会話セッションを停止します。

電子機能が使えないときも、枕として使えることを基本にします。まず1台で会話・トントン・停止までを通し、2台連携はその後に検討します。

## 最小構成（MVP）

- 枕として使える本体と、柔らかいしっぽ
- 短い音声会話を1往復できること
- 返答待ちに、発話を遮らない短い音声の相づちを返せること
- 会話に合わせてしっぽを小さくトントンさせられること
- ユーザーが手元で停止できること
- 通信切断やタイムアウト時に、しっぽを停止できること
- 電子機能を停止しても枕として使えること

睡眠時間の記録、眠気の推定、夕方の通知、長期記憶、細かな人格設定、2台連携はMVPの後に検討します。

## プログラムの構成案

このリポジトリの `ClientSide` と `ServerSide` を、次の役割に分ける想定です。Android Web音声APIを [音声会話API仕様](ServerSide/VOICE_API.md)、Pi 4デバイスAPI案を [Raspberry Pi 4 API仕様](ServerSide/RASPBERRY_PI_API.md) にまとめました。音声会話APIコードはありますが実機確認は未完了です。Pi 4の音声API案はAndroid Web MVPの音声経路では使用しません。

### 開発作業の担当分け

| 作業 | 主な担当範囲 | 役割 |
| --- | --- | --- |
| Androidクライアント | `ClientSide/` | WebView、サーバーURL、マイク権限、録音・再生、停止操作 |
| ダッシュボード／HTTP入口 | `ServerSide/app/dashboard/`、`ServerSide/web/` | 設定画面と配信、設定API、音声会話APIのHTTP受付 |
| STT・LLM・TTS | `ServerSide/app/voice/` | 各モデル接続、STT→LLM→TTSパイプライン、セッション、相づち |
| 共有設定 | `ServerSide/app/settings_store.py` | ダッシュボードで保存した設定を音声処理から読む。参照WAVの検証・管理 |
| Raspberry Pi 4・しっぽ | `ServerSide/app/tail_mcp_server.py`、`ServerSide/RASPBERRY_PI_API.md` | MCPから機器APIを呼ぶ。初期音声MVPの後に実装・統合 |

### ブランチ運用

作業は `main` から用途ごとの `codex/<担当>-<作業>` ブランチを作って進めます。次の名称は作業単位の例であり、事前にブランチが存在することを示すものではありません。

| ブランチ名の例 | 主な作業 |
| --- | --- |
| `codex/android-client` | Android WebView、マイク、録音・再生、端末側停止 |
| `codex/server-dashboard` | ダッシュボード画面、HTTP入口、設定API |
| `codex/server-voice-pipeline` | STT、LLM、TTS、音声セッションと相づち |
| `codex/raspberry-pi-tail` | Pi 4デバイスサービス、MCP、しっぽ制御 |

担当をまたぐ変更では、先に `VOICE_API.md` または `RASPBERRY_PI_API.md` と関連要件書を更新し、同じAPI契約に合わせます。作業ブランチで差分を確認してから `main` に統合します。`main` は統合先とし、個別作業を直接積み重ねません。

### ClientSide（Androidブラウザーを基本とするスマホ画面）

- 接続先と接続状態の表示
- Androidマイクによる会話開始／停止と端末音声状態の表示
- 本返答の再生と、重複・遅着音声の確認。相づちと再生結果通知は今後の対応
- 会話・トントンの開始／停止
- 音量、トントンの有効／無効と速さの設定
- 設定の適用確認と、停止未確認・切断・再生失敗の表示
- 声、キャラクター、話す頻度の設定（MVPでは後回しでもよい）
- Androidスマートフォンを優先して動作確認

設定・音声会話画面は `ServerSide/web/` に作成し、STT・TTS・会話のふるまいを保存できます。Irodori-TTS用の参照WAVもアップロード・保存・削除でき、サーバーが形式・長さ・容量を検証します。Android WebViewの録音・送信・返答再生とセッションAPIのコードを追加しました。HTTPS環境、相づち・再生完了通知、Pi 4のMCPしっぽデバイスサービス、Android実機確認は未完了です。

### ServerSide（会話処理・連携の案）

- `web/` の設定ダッシュボードと、サーバー側の設定保存API

- Android Webからの音声受信、STT→LLM→TTSの処理、返答音声の配信
- 会話セッションの開始・終了、期限・停止世代の管理
- 会話セッションの開始・終了管理
- LLMからMCP経由でしっぽの開始・停止・状態確認を呼び出す
- MCPサーバーからRaspberry Pi 4への固定動作指示（HTTPS/JSON API）
- 失敗・切断・タイムアウト時の停止処理

自作コードは `ServerSide/app/` にまとめ、音声処理を `voice/`、HTTPサーバーを `dashboard/` に分けました。`voice/pipeline.py` がSTT・LLM・TTSをつなぎ、`voice/sessions.py` が会話セッションを管理します。モデル・HTTPS環境・Android実機は未確認です。詳細は [ServerSideの構成](ServerSide/README.md)、[音声API](ServerSide/VOICE_API.md)、[自作ServerSideアプリの説明](ServerSide/app/README.md) を参照してください。

モデル候補として `faster-whisper-small`（STT）、`Gemma 4 26B-A4B（Q4_K_M）`（LLM）、`Irodori-TTS 600M v3 VoiceDesign`（TTS）をコードの初期設定にしています。接続先・デバイス設定とパイプラインは実装しましたが、モデルの準備、動作環境、応答速度は未確認です。

### Raspberry Pi 4・しっぽ機構

- SG90サーボで軽い布・スポンジ製のしっぽを小さく上下させる
- サーボは外部5V有線給電とし、Pi 4のGNDと共通化する。GPIOからサーボ電源を取らない
- 電源を切れる手元停止と、Pi 4側の動作タイムアウトを設ける
- 0〜12°はCAD上の表示例であり、実機の角度・押す強さ・騒音・発熱は実物で調整する

Pi 4のデバイスサービス、サーボ信号回路、しっぽの動作上限と手元停止は未確定です。`RASPBERRY_PI_API.md` には将来の機器API案も記録していますが、Android Web MVPの音声はスマートフォンで録音・再生します。

## データの流れ（概念）

```text
Android WebViewマイク → サーバー(STT → LLM → TTS) → Android WebViewスピーカー
                                             │
                                             └─ MCP → tail_mcp_server → HTTPS → Pi 4 GPIO → SG90
スマホの設定・会話操作 → アプリサーバー
```

音声はAndroid WebViewからサーバーへ1発話ずつ送り、返答音声を期限付きで取得する契約です。セッション・発話・停止世代を使い、停止後の遅着結果を拒否します。相づち配信と再生完了通知、Pi 4しっぽデバイスサービス、実機確認は未完了です。

## 動作の流れ

1. ユーザーがAndroid画面で開始し、マイク権限とサーバー接続を確認する。
2. Androidの録音をサーバーへ送り、STT・LLM・TTSで短い返答を作る。
3. 返答の生成に時間がかかる場合は、相づちを短く一度だけ再生する。
4. Androidのスピーカーで返答を再生し、明示的なトントン要求があればPi 4のしっぽを優しく動かす。
5. 「おやすみ」は最後の短い返事で終了する。停止ボタンは即時に端末音声と会話セッションを止め、しっぽ停止は独立した制御要求として扱う。
6. 通信断、異常、またはタイムアウト時は、しっぽを停止できる状態にする。

音声の開始条件、返答中のトントン動作、タイムアウト時間などの細部は実機統合時に決定します。

## 相づち（MVP必須要件）

返答を待つユーザーに、聞いていることを伝える短い音声の相づちを提供します。相づち機能自体は必須とし、再生タイミングや使用する言葉は実機で調整します。

- ユーザーの発話中には再生せず、発話が終わってから返答を待つ間に使う。
- LLMの返答を待たせる場合に、短い相づちを1回だけ再生する。返答音声と重ねない。
- 「うん」「そっか、聞いてるよ」など安心感のある短い候補を用意し、同じ言葉を連続で繰り返さない。
- 夜間に大きな音で驚かせないよう、相づちも設定音量に従う。停止・おやすみ操作後は再生しない。
- AI_Secretaryにある相づち音声の事前生成・キャッシュと、最初のLLM文節が届くまでの待ち時間を埋める処理を再利用候補とする。

相づちの候補音声を事前生成する処理と、LLM待ちが設定時間を超えた場合の通知コールバックは実装済みです。Android Web APIへの相づち配信・再生調停、停止時の破棄は未実装です。

受け入れ条件は、返答待ちが設定時間を超えた際に1往復につき最大1回だけ再生すること、ユーザーの発話や本返答に重ならないこと、停止操作で再生中・待機中の相づちを停止できることです。本返答が先に準備できた場合は相づちを省略します。

## 実装・確認の順序

1. Android WebViewからSTT → LLM → TTSの音声1往復を確認し、返答時間を測る。
2. Raspberry Pi 4のデバイスサービスにしっぽAPIを実装し、MCP Inspectorからタップ・停止・状態取得を確認する。
4. LM StudioへMCPサーバーを登録し、明示的な「トントンして」でだけツールを呼ぶことを確認する。
5. Android Webの会話経路とPi 4のしっぽ制御を接続し、1台で「開始 → 会話 → トントン → 終了」を統合する。
6. 実機で停止・再起動・通信切断からの復帰を確認してから、2台連携を試す。

## 仕様を確定する項目

- Androidブラウザーの録音形式、再生形式、API上限に対する対象端末の対応状況
- Android WebViewとサーバー間のHTTPS接続、音声API認証、通知・再接続方法
- セッションと停止世代の識別、遅着結果とMCP動作を拒否する方法
- MCPとPi 4でセッション許可・停止世代を連携し、遅れて届く開始要求を拒否する方法
- Raspberry Pi 4側の角度制限、ウォッチドッグ、電源遮断式の停止手段をどう実装・検証するか
- Pi 4の電源容量、GPIO信号回路と配線
- サーボの実機動作範囲、しっぽの接触位置、停止時間
- STT／LLM／TTSの採用モデル、サーバー・GPU環境、応答速度
- 設定項目、通信メッセージ、音声形式、切断時の再接続方法
- 2台連携をデモの必須要件とするか
- ロボットの正式名称、キャラクターの口調

## デモの基本シナリオ

「今日はちょっと寂しい」→Androidスマートフォンへ話す→短い返事→「トントンして」→Pi 4のしっぽが動く→「おやすみ」→短い返事のあと静かに停止する。

入眠する場面はデモ上の演出です。会話と動作が使えない場合でも、枕として使える状態を保ちます。
