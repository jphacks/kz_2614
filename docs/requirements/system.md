## 1. 製品の目的と今回見せたい体験

寝る前に話したい、一人でも誰かの気配を感じたいという場面に向け、**スマホでの音声会話と、きつね型人形のしっぽによるトントン**を組み合わせます。他の人の操作を人形へ届ける簡易フィードバックも、今回見せたい体験に含みます。

スマホがマイク・スピーカー・操作画面、PCがVAD/STT/LLM/TTS、ESP32が入力とサーボを担当します。スマホの製品画面はWeb/PWAです。別実装のAndroidネイティブアプリと混同しません。Raspberry Pi経由の案は現行構成に含めません。

目標とするデモの順序は、**ログイン・人形確認 → 時間設定 → 一人で会話 → トントン → 他者フィードバックへ切替 → 停止 → 記録確認**です。現時点では、これを最初から最後まで実行できる状態には達していません。

| 状態表記 | 意味 |
| --- | --- |
| main実装 | mainにコードがある。公開配備・実機成功を意味しない |
| PR実装 | PR #25にコードと自動検証がある。main・公開サイトへ未反映 |
| 未統合 | 関係する部品はあるが、製品としての接続がない |
| 未実装／未確定 | コードがない、または振る舞い・採用方式を決める必要がある |
| 実機未確認 | 対象端末・ネットワーク・人形を使った合格記録がない |

## 5. 音声会話の仕様

- 利用者が毎回開始し、マイクを選んで許可する。PRはAPI応答を検査し、認証HTML・不正JSON・接続失敗では開始成功にしない。録音準備完了後から利用時間を記録する。
- 16kHz・mono・PCM16LEを無音/返答中も送信する。PC側のVADが発話を区切り、STT→LLM→TTSへ渡す。途中認識は確定認識で修正され得る。
- TTSは既存の文節を合成した後、Webへ最大100msのPCMフレームで送る。モデル内部の合成途中サンプルを直接出す方式ではない。
- 返答中に話しかけた場合は古い返答を破棄し、新しい発話へ切り替える。会話の終了とは区別する。相づちはPCが判断し、1ターン最大1回、本返答と重ねない。
- PRの会話期限は開始時の15/30/45/60/75/90分で固定し、設定変更は次回から。サーバーの無操作15分TTLとは別の制約。
- 手動、期限、画面非表示、ページ終了、入力障害、別タブ開始で端末音声を止める。再読込や画面復帰では自動再開しない。画面ロック中の継続通話は保証しない。
- PRの停止は端末を直ちに解放して記録し、サーバーへのDELETEは別に確認する。応答期限5秒、JSON・対象session・停止状態を検証し、確認できない場合はその旨を表示する。
- 音声経路の古いsession/turn/generationの結果を再生しない。短い通信断は有界の再送、回復できない場合は停止して手動再開する。
- 「おやすみ」への短い応答と相づち抑止はあるが、最後の返答を再生し終えて自動終了する制御は未完了。

モデル・細かな期限・再送容量は [サーバー仕様](server.md) と [HTTP音声API](../api/voice-http.md) を正本とし、実行時の設定と過去のモデル測定結果を区別します。

## 6. トントンと他者フィードバック

### 製品のモードと機器内部モード

| 利用者向けの選択 | 意図する動作 | 現行との対応 |
| --- | --- | --- |
| 会話連携 | 現在の会話の明示要求に応じ、許可した人形だけを有限動作 | 実機MCP接続は未統合。PRのボタンは利用不可 |
| 他者フィードバック | 許可した操作者のReader入力をFollowerへ届ける | 基礎経路は`teleop`。アプリでの操作者選択・権限・切替は未実装 |
| 停止 | 動作と追従を止め、結果を確認する | 機器APIあり。製品の音声停止との一括接続は未実装 |

これらは製品の選択肢です。Follower内部の`teleop`・`api`・`konkon`・`neutral`・`relax`と同じ名前のAPIが存在するわけではありません。

製品へ統合する際には、現在の入力を停止し、対象機器と新しい操作者の許可を確認してから切り替えます。切替途中や接続不明時に両方の入力を受け付けないこと、切替前の遅着指令で動き出さないことを受け入れ条件とします。この製品側の排他・権限制御は未実装です。

### 現在の機器契約

- Readerは可変抵抗の値を指令へ変換し、Followerは3台のSG90へPWMを出す。接触センサーによる反応とは別の入力である。
- 有限タップは0.5〜5秒、記録上の実機上限は0.3回/秒、60秒枠の要求動作時間合計は10秒まで。片側の端への到達を1回と数える。
- PC希望頻度の保存範囲0.3〜1.0Hzを、そのまま実機へ適用しない。会話に公開中なのは`set_tail_frequency`と`get_tail_frequency`だけで、`device_confirmed=false`を返す。
- `/api/tail/stop`は最後の指令角を保持し、Reader追従も止める。`neutral`は中立へ移動、`relax`はPWM停止で、どれも物理電源遮断とは異なる。
- 有限動作の終了や停止後は自動でReaderへ戻らない。中立/脱力の解除、Reader復帰を無断で自動化しない。
- 機器の`feedback=command_only`は指令状態で、接触・実角度・機械的な停止の測定ではない。HTTP成功、機器の指令状態、操作者の実機観察を分けて記録する。
- 現行Follower APIはsession_idや停止世代を受け付けない。会話側の取消・権限・遅着拒否を設計し、未対応フィールドを追加送信して代用しない。

配線・校正・モード詳細は [ESP32仕様](esp32.md)、動作契約は [機器HTTP API](../api/esp32-http.md)、統合条件は [MCP統合仕様](../esp32/mcp-integration.md) を参照します。

## 7. 本人・アプリ・人形の認証と紐付け

**公開ページにログインできることと、その人が特定の人形を操作できることは別です。** 現行のPC/機器APIは開発用の認証なし構成で、Passportの保護だけではユーザー別の所有・共有権限を実装したことになりません。

| 確認対象 | 製品として必要な条件 | 現状 |
| --- | --- | --- |
| 本人識別 | 信頼できる認証結果から利用者を識別する | 製品UIで本人情報を取得する連携なし |
| 人形識別・登録 | 接続先と実際の人形を対応付け、所有・共有を登録する | 登録・紐付けAPIなし |
| 操作権限 | 音声会話と機器操作を誰に許すかサーバー側で判定する | ユーザー/人形単位の判定なし |
| 他者操作 | どの人からどの人形への操作を許すか、解除も含める | Readerの接続先設定のみ。共有権限の代わりにならない |
| 機器との信頼関係 | 正しいサーバー/Readerと機器の組を確認する | ESP側の認証未実装 |
| 失効・切断 | 操作継続を止め、未接続/権限なし/停止未確認を区別する | 製品全体としては未統合 |

user_id・device_id等の具体スキーマ、登録手順、共有・失効方式は未確定です。ここでは必要な条件だけを定義し、存在しない認証APIを実装済み契約として書きません。画面のdisabled表示だけで権限を守ったことにもなりません。[課題 #10](https://github.com/jphacks/kz_2614/issues/10)

PRは設定とID別記録を分離し、新形式の記録キーを100件保持します。表示は旧記録を含む最新100件、旧キー自体は削除しません。複数タブはstorageイベントで同期し、保存失敗は警告して未保存と表示します。同一アカウントでログインしても端末間では同期しません。

通常の音声・会話本文をブラウザーの日記やログへ保存しません。サーバー内の会話コンテキストと、永続化する日記・要約は別です。要約の内容・同意・保存期間・削除方法は未確定。明示登録した参照WAVや相づち素材は既存の保存対象の例外です。

PRのSWは静的素材だけを対象にし、API・認証callback・音声応答をキャッシュしません。オフライン表示ができても会話はできません。URLのscheme/host/port、ブラウザー、サイトデータ消去で保存領域が変わります。[製品Web仕様](web-product.md)
