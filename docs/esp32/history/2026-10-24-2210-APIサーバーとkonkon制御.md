# APIサーバーとkonkon制御

2026-10-24。Followerは以前からHTTPサーバーを持ち、`POST /api/angle`で指定角度へ動いて保持できる。今回、ユーザーの指定に合わせて`POST /api/konkon`へ`start_angle`、`end_angle`、`speed`を追加した。開始角度と終了角度は異なる0～180°の整数、速度は先端の指令角度で1～180°/秒。現在角度から開始角度へ進み、その後は開始角度と終了角度を往復する。3台のSG90には同じPWM幅を出す。20 msごとに`millis()`で指令を更新し、HTTP処理を止めない。Wi-Fi切断時は往復を止め、最後の指令角度を保持する。

`POST /api/angle`を往復中に送ると、往復を解除して指定角度へ動いて保持する。`POST /api/mode`の`mode=teleop`でReaderの可変抵抗器へ戻り、`mode=neutral`で3台を中立1500 µsへ移す。`GET /api/status`は`mode=konkon`、現在指令角度、開始角度、終了角度、速度、次の目標角度を返す。中立中の角度・往復指令、API操作中のReader指令は409で拒否する。起動時のモードは従来通りテレオペ。保存済みのパルス全範囲600～2400 µs、0°側の丸まり追加100 µsも維持した。

Arduino ESP32 core 3.3.12でFollowerをビルドし、MAC `70:4b:ca:82:40:18`のESP32へ書き込み、フラッシュのハッシュ照合に成功した。試験のため、MAC `70:4b:ca:4e:02:60`のReaderへ一時的なHTTPクライアントを入れ、同じアクセスポイント経由でFollowerの`192.168.100.111`へリクエストした。途中でUSB差し替えがあり、最終確認時のポートはReaderがCOM6、FollowerがCOM11。PCは別ネットワークなので、PCからのHTTP直接アクセスではない。

`GET /api/status`はHTTP 200で、保存済みの丸まり調整100 µsとGPIO18・19・21を返した。`POST /api/angle`の`angle=90`はHTTP 200、`mode=api`、1500 µs。`POST /api/konkon`の`start_angle=60&end_angle=90&speed=15`はHTTP 200、`mode=konkon`。続く状態取得で先端の指令角度90→74→85→67°、折り返し目標60→90°の変化を確認した。`POST /api/angle`の`angle=75`で`mode=api`へ移り、続く状態取得でも75°を保持。`POST /api/mode`の`mode=teleop`でテレオペへ復帰した。Readerの元のスケッチを再ビルドして書き戻し、フラッシュ照合成功。Followerは可変抵抗器から0°指令を再受信し、3ピンのHIGH時間は約1101～1102 µsだった。

ユーザーが実物を見た再試験では、60～90°・15°/秒は方向性は合うが、動きの幅が小さく遅いとの評価。そこで`start_angle=0&end_angle=180&speed=60`を約20秒間実行した。HTTP 200で`mode=konkon`となり、状態APIで現在角度と折り返し目標の変化を確認。ユーザーは幅と速さが良く、異音・突き当たり・発熱・リンク同士の接触もないと報告した。`angle=75`で往復停止、`mode=teleop`でテレオペへ戻し、Readerを元のスケッチへ再書き込み・フラッシュ照合した。Followerの`v`ではReaderからの0°指令と3ピンの約1101～1102 µsを再確認した。今回の実機で気に入った設定はAPIリクエストで毎回指定するもので、不揮発メモリへ往復設定を保存する仕組みではない。

可動部の実角度や速度は計測器で測っていない。Wi-Fi切断時の停止処理とAPIの不正入力・競合応答は実機では未試験。PCから直接APIを利用する端末はESP32と同じネットワークに接続する。詳細とコマンド例は`README.md`を参照。
