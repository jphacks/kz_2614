**最新の変更: プロトタイプとして動作を優先するユーザー指定により、提案PythonとESP32 Followerのトークン認証を削除した。`TAIL_DEVICE_TOKEN`の設定・Authorizationヘッダーは不要。**先輩に渡すファイルは[2026-10-25_0313_tail_mcp_server.py](2026-10-25_0313_tail_mcp_server.py)。以下の元リポジトリ調査と401の試験結果は、認証削除前の履歴である。

## 結論: 必要な動き

- 会話中にユーザーが**明確にトントンを希望したときだけ**短時間動かす。「寂しい」という発話だけでは動かさない。
- 止めてほしい、会話の停止、手元停止、異常、通信断では、LLMの返答を待たず停止できること。停止後に届いた古い開始指令を拒否すること。
- 動作状態を確認する。HTTP受付、ESP32が指令中、物理的な尾の動作確認を混同しない。
- 先輩側の案は布・スポンジ製しっぽを小さく上下させるRaspberry Pi 4＋SG90の設計だった。一方、**実機はESP32 Follower＋SG90 3台、直列リンク**。今回のユーザー指定でトントンの振り幅は前回試した先端指令0°～180°を基準にする。前回の実機で0°～180°・60°/秒は良好と確認されたが、より速い動作は未検証。

## 調査した元のLLM側が送る要求

`STTLLMTTS/llm/lm_studio.py`はLM Studioへ`mcp/nen-gitsune-tail`プラグインの`tap_tail`、`stop_tail`、`get_tail_status`だけを許可する。既定の`TAIL_MCP_ENABLED`は`false`。システムプロンプトは、明示的な希望があるときだけ開始し、停止希望時は止め、角度を直接指定しない方針。

`STTLLMTTS/tail_mcp_server.py`はLM Studioにstdioで起動され、HTTPクライアントとしてデバイスへ次のように送る。`TAIL_DEVICE_URL`はプライベートIPまたは`.local`だけを許容し、`TAIL_DEVICE_TOKEN`をBearerヘッダーで送る。HTTPの接続期限は1秒、全体期限は3秒。`TAIL_CONTROL_ENABLED=false`が既定で、開始時はこれを検査するが停止は有効設定に関係なく送る。

| MCPツール | 受信する引数 | 現行MCPが送るHTTP |
| --- | --- | --- |
| `tap_tail` | `duration_seconds` 0.5～5.0（既定2.0）、`taps_per_second` 0.3～1.0（既定0.6） | `POST /api/tail/tap`、JSON `{"duration_ms":2000,"rate_hz":0.6}` |
| `stop_tail` | なし | `POST /api/tail/stop` |
| `get_tail_status` | なし | `GET /api/tail/status` |

現行MCPは成功応答中の`state`を文字列化する。デバイス応答がJSONでない場合も空辞書に置き換え、`unknown`を含む「sent」文字列を返してしまう。機器受付と物理動作の確認は別に扱う必要がある。

## 先輩側がデバイスに想定していた要求と食い違い

先輩側の設計資料`Programs/ClientSide/Raspi4Ver/RASPBERRY_PI_API.md`では**別の将来契約**`/api/v1/tail/tap`・`stop`・`status`を定義している。Bearer認証付きJSONで`command_id`、`session_id`、`stop_generation`、`duration_ms`、`rate_hz`を受け、受付時はHTTP 202、重複要求と古い停止世代を拒否し、機器状態を照会する構想。現在のMCPコードは旧`/api/tail/...`を呼び、これら3つの識別子を送らない。Pi 4側のデバイスサービスも未実装。LLMサーバーの停止処理とMCP停止指令の独立した接続も未実装。

こちらの従来ESP32 APIは`POST /api/angle`、無期限に往復する`POST /api/konkon`、`POST /api/mode`、`GET /api/status`で、POST本文はフォーム形式。認証なしのため、MCPが送るJSON＋Bearer＋旧`/api/tail/...`とはそのままでは接続できなかった。

## このESP32作業フォルダで実装した接続口

- `ESP32-Follower/ESP32-Follower.ino`に**元MCPのパスと一致する3つのHTTP API**を追加。最新のプロトタイプはトークン認証なしで、`tap`はJSON本文と動作範囲を検査する。
- `tap`はGit管理外`TailConfig.h`の安全確認済み両端を往復し、要求された500～5000 msで自動停止して最後の角度を保持する。`rate_hz`は**片端到着を1回**と定義し、先端の指令速度を`(終了角度－開始角度)×rate_hz`度/秒にする。実機試験時の0°～180°・0.3回/秒は約54°/秒。先輩側MCPの既定0.6回/秒なら約108°/秒だが未検証のため、ローカル設定で上限0.3に制限する。実際の接触回数と機械速度は未計測。
- 次のタップは動作中にHTTP 409で拒否する。60秒間に受付ける動作時間の合計は最大10秒。電源再投入でこのソフトウェア上の予算はリセットされる。
- `stop`は開始許可が無効でも往復とテレオペを止め、最後の角度で保持する。`status`は`idle`/`tapping`/`moving`、残り時間、`feedback:"command_only"`を返す。サーボの位置センサーはない。
- `TailConfig.example.h`を追加し、実際の`TailConfig.h`はGit管理外にした。配布用の既定値は制御無効、両端90°・90°で動作不可、確認済み速度上限0.3回/秒。認証削除に伴い、実設定・テンプレートからトークン定義を削除した。
- 従来のReaderテレオペ、角度API、無期限konkon、脱力モードは保持する。MCPタップ中はReader指令をHTTP 409で拒否し、動作終了後も明示的な`mode=teleop`までReaderへ戻らない。

## 検証と残る限界

- 2026-10-25 03:40 JST、ユーザー指定でトークン認証をPython・ESP32双方から削除。PythonはMCP SDK 2.3.0でトークンなし送信を含む17テストが成功。Followerのトークンなし版をビルドしCOM6へ書き込み、フラッシュ照合成功。認証ヘッダーを一切送らない一時Readerから、`GET /api/tail/status`と`POST /api/tail/stop`のHTTP 200を確認した。中立中の正しいtapは409、速度0.6回/秒のtapは400で拒否され、状態は90°中立・1500 µsのまま。サーボを往復させる試験は行っていない。
- トークンなしAPI確認後、Reader（COM12）へ元の可変抵抗器用プログラムを書き戻し、フラッシュ照合成功。FollowerはReader復旧後も90°/1500 µsを保持し、GPIO18・19・21は約1502～1503 µs。校正値は変更していない。2台のシリアルモニタは終了済み。
- ESP32 core 3.3.12でFollowerと試験用Readerのビルド成功。Follower（MAC末尾`40:18`、この日のCOM6）へ書き込み、フラッシュ照合成功。
- 一時的なReader（MAC末尾`02:60`、COM12）から、認証付き`GET /api/tail/status`はHTTP 200、認証なしはHTTP 401を確認。`POST /api/tail/tap`の`duration_ms=2000, rate_hz=0.3`はHTTP 200で`state=tapping`、2秒後は`state=idle`、最後の指令角107°、3つのGPIOのHIGH時間約1558～1559 µs。Followerログにも期限で停止と表示された。
- 2秒の要求では0°～180°の全域へは到達しない。続く5秒・0.3回/秒の試験はHTTP 200で受理され、期限後`idle`、最終指令角160°、3ピンのHIGH時間約1735～1736 µsを確認した。初回のユーザー回答は異常ありだったため、直ちにシリアル`d`で3台のPWMを停止し、`mode=relax`・`pwm_enabled=false`をHTTPで確認。後でユーザーは「異常というわけではないが、動作中にサーボ周辺ががたがた揺れて見えた」と説明した。
- ユーザーの依頼で`mode=teleop`を経由して`POST /api/angle angle=0`を実行し、HTTP 200、3ピン約1101～1102 µsを確認。続いてユーザーが90°中立を希望したため`mode=neutral`を実行し、HTTP 200、3ピン約1502～1503 µsを確認。ユーザーは実機も中立で異常なしと確認した。
- 再度ユーザーが見ている状態で、90°中立から5秒・0.3回/秒を試し、0°側から最終指令角177°まで移動して期限停止。ユーザーは**問題なく動いた**と確認した。途中停止の初回試験では、HTTP 200で`state=idle`、角度13°のまま数秒後も変化しないことと3ピンのパルス約1160 µsを確認した。
- 2026-10-25 03:06 JSTに、速度上限0.3回/秒と近い端から向かう制御を含む最終版をFollower（COM6、MAC末尾`40:18`）へ書き込み、フラッシュ照合成功。ローカルのGit管理外`TailConfig.h`はMCP API有効、範囲0°～180°、上限0.3回/秒。BearerなしのstatusはHTTP 401、認証付きのstatusはHTTP 200で`max_rate_hz=0.300`、0.6回/秒のtapはHTTP 400を確認した。配布用`TailConfig.example.h`は引き続き無効・90°～90°である。
- 最終版でユーザーが見ている状態で5秒・0.3回/秒を再試験し、HTTP 200で開始、5秒後に`state=idle`・最終指令角177°を確認。90°中立へ戻し、ユーザーは実機が正常に動いて異音・発熱・接触なしと確認した。続く途中停止試験では5秒要求の開始後に`POST /api/tail/stop`を送信し、HTTP 200で角度24°を保持、2秒後も24°で停止。その後90°中立へ戻し、ユーザーは途中停止と中立復帰、異音・引っ掛かり・接触なしを確認した。
- 一時的なHTTP試験プログラムをReader（COM12、MAC末尾`02:60`）から除き、元の可変抵抗器用スケッチを書き戻してフラッシュ照合成功。Readerの`v`は`ADC raw: 0; active min/max: 0/4095`、Followerの`v`は3ピン約1502～1503 µs。Followerシリアルの`n`で**現在は90°中立モード**。Followerを再起動すると通常の自動テレオペが始まり、現状のつまみ0°へ動くため注意。LLM側の開始許可は引き続き無効。
- 先輩側MCPの既定速度0.6・最大速度1.0、通信断、短い連続要求、電源電流の実測は未確認。LLM側には既定値と許容上限を0.3へ下げる変更を依頼する。
- 現行MCPにはセッションID、停止世代、要求IDがなく、ファームウェアの旧APIもそれらを受けない。**停止後に遅れて届く旧開始指令の拒否は実現できていない**。サーバー側でセッション許可を検証し、将来はバージョン付き機器APIへ移行する必要がある。機械的な電源遮断スイッチも別途必要。

- `idle`だけでは中立・脱力による開始不可を見分けられなかったため、`get_tail_status`が既存の`GET /api/status`も照会し、`mode`と`ready_to_tap`を返すようにした。中立・脱力、未設定の動作範囲、対応外の速度上限、動作無効の場合はfalse。60秒当たりの残り時間予算は開始受付時にESP32が判断するので、trueでも受付を保証する値ではない。

- ツールの説明を、開始の戻り値がESP32への指令受付を意味する表現へ修正した。物理位置・接触を検出する機能はない。
